# Verify

1. **Resolve target and spec:** Target session integration when present, else the working tree, unless the argument names a revision. For a revision other than checked-out HEAD, create a temporary detached checkout under `<session>/.state/`, report-only: apply no fixes; remove the checkout after verification. Reuse the bound or session spec. If absent, author a spec from the full discussion and diff as for standalone code review, label inferred requirements, and add no authoring approval gate.
2. **Run checks:** When `implement` invokes this stage, its all-checks run already passed on this HEAD; pass `checks passed` directly when at least one executable check ran and skip re-running `check run`. For standalone `verify`, when targeting the session integration itself (not a separate named revision checkout) and `status show` reports both a bound plan and a session integration, run [checks](../toolkit.md#check-run) (`check run`) first. If `check run` fails, do not launch the verifier: route to repair under [routing](../../SKILL.md#routing) and rerun before launching the verifier. Pass `checks passed` in the verifier focus only when at least one executable check ran and passed on the target tree; if `check run` ran zero commands (for example `Automated Tests: None` with only review criteria) or no bound integration is targeted, omit `checks passed` so the verifier runs the repository baseline. A failed check or baseline is not runtime proof and prevents outcome `proved` until fixed.
3. **Choose cycle and launch verifier:** Choose cycle one above the highest verification record, or 1; an interrupted run retains its cycle. Every new cycle launches fresh. When nothing runnable can be proved and checks did not fail, skip launch and record a no-op reason. Otherwise render [brief verifier](../toolkit.md#brief-verifier) with `checkoutPath`, `base`, `specPath` and `focus`. Start `focus` with `Cycle <n>` using the chosen ledger cycle, add `checks passed` when at least one executable check ran and passed on this tree, include `no test edits` for a named revision other than HEAD or a post-review re-check, and include `test edits permitted` for initial implement verification and standalone verification on the current checkout. Launch the utility subagent on its returned values; if the host has no launch tool, run verification inline under the same boundaries. Inspect its delta.
4. **Handle approvals:** The verifier finishes unblocked checks before returning `NEEDS_APPROVAL` with a batched request. Use the [Decision Frame](../decision-frame.md) to obtain and record the user's approval quote before risky actions; continue the same subagent. A declined check is `not proved` and is a limit, not an issue. Read-only calls, local servers and disposable resources created and removed by the verifier need no approval. Persistent or shared state changes, external messages, paid calls and non-local actions require approval.
5. **Persist report, rule issues and fix:** The report and artifacts live under `<session>/verification/` and stay outside the delivered diff. Store artifacts in the cycle's subdirectory. A continuation may assign new artifact paths there; the verifier writes those artifacts and returns results inline, never rewriting `report.md`. When the host refuses the report write, the verifier returns the full report text and the orchestrator persists it under `<session>/verification/` with its evidence; a refused write needs no user ruling. Append each continuation result to the report under a follow-up heading with its approval quote or issue IDs. New cycles append a cycle heading and preserve earlier content. Verify each issue claim against intent and evidence; record a ruling with subject `verification:<cycle>:V<n>` and key `ruling:verification:<cycle>:V<n>` as accepted, rejected, duplicate or deferred. On resume rule any reported issue without a ruling before continuing. Fix accepted issues on the verified tree and continue the same verifier to re-check only those issues. Escalate recurrence through the Decision Frame; escalate when three fix rounds per issue finish with an accepted issue still open. Standalone on the working tree leaves fixes there, with no delivery step.
6. **Record outcome:** After settlement append an `integrate` verification record with cycle, outcome `proved`, `partial` or `no-op`, full tested `head`, nonblank reason and open accepted unfixed issues. `proved` and `no-op` require empty open; report is required for `proved` and `partial`. Record the no-op reason even when the verifier chose it. Include report and artifacts as session-relative paths or HTTPS links. Set `dirty: true` when the standalone tested tree has uncommitted changes.
