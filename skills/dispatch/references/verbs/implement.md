# Implement

Resolve the full governing spec and plan, following Parent pins through a design when present. For an objective, author the spec and plan first. For a design, deliver its ordered increments. The [toolkit contract](../toolkit.md) owns tool arguments and result shapes.

1. Lint the artifacts. Resolve outstanding plan findings, failed slots and escalations. If this invocation authors the plan, propose its level after lint; record it under [run level](../spec-stage.md#run-level) before the first review. A review or implementation may raise it under the same rule. Run a new plan review only when no completed plan review in the session covers the current spec and plan hashes, or when the user asks; a settled plan from `plan` is not re-reviewed. Bind spec, plan and optional design in the ledger with the applicable user approval tuple.
2. Run baseline checks and retain failures. Choose bounded repairs or reported limitations against governing intent.
3. Create each ready task worktree, render its brief and launch a native writer there. Honor prerequisite ordering and configured native capacity. A brief carries the whole spec, shared plan context, task scope, criteria and checks.
4. Keep each writer running through inspection, discriminating RED tests, implementation to GREEN, cleanup and affected-file verification. Writers edit only assigned paths and run no Git write commands. Their result report names changed behavior, checks, concerns and artifacts. Missing RED is a review finding.
5. Inspect the actual delta and evidence. Submit the candidate with the worktree tool, integrate it and run criterion and contract verification on the integrated tree. A submitted candidate alone does not release prerequisites; verified integration does.
6. Review code and judge the durable or FINAL coverage named by each transient criterion's Covered by against the quality bar. A green suite cannot detect missing protection. Resolve every MUST: accepted fixes require review; rejected findings require explicit reviewer confirmation under [review rules](../review-rules.md#rulings-and-fix-scope); duplicates retain their original obligation. Pending or escalated confirmations block pruning, delivery and report completion; unruled and deferred MUST findings also block pruning. Apply accepted fixes in integration, commit and rerun criterion and contract checks. Require a completed full review with no failed slots, open escalations or unresolved accepted fixes. Normally it must cover the exact integration HEAD; recorded, verified accepted SHOULD fixes from a final completed round at or above the cap may use the exception in [review rules](../review-rules.md#review-provenance-and-applicability). The exception requires current criterion and contract checks. The no-fix path reuses the exact completed review.
7. After code review and before pruning or delivery, inspect every criterion marked `Evidence: review`. Check each declared scenario and status, gather criterion-specific evidence, then present all required user manual-complete decisions with their evidence in one user request. Record each user's decision in the existing user-only manual record after they respond; keep delivery pending while any required decision is absent. Route missing or failed automated evidence through existing verification and escalation. If no manual decision is pending, continue without a user request.
8. For transient plans, call the prune tool, then run final verification as defined in [toolkit lifecycle](../toolkit.md#worktree-prune). Preserve pre-prune RED/GREEN evidence and source commits. Deliver the exact verified source as unstaged caller changes (no caller commit) only after final checks pass. Complete the report only after delivery; its completion check remains the final evidence check. Clean owned worktrees. Follow [delivery preconditions and recovery](../toolkit.md#worktree-deliver) for a dirty caller or interrupted delivery. For failures or interruption, retain the pruning records and work and follow its recovery rules.

When diagnosing a failure requires reading many files, consider a [follow-up explorer](../grounding.md#follow-up-explorers).

Treat scope overrun, concerns, conflicts and red baselines as information with options. Verify each claim, then repair, clarify the plan, retry, retain for recovery or escalate a material user decision. Tool refusals identify an operation prerequisite; inspect the result rather than inventing success or bypassing it. Waivers and manual-completion records must quote the user's actual words.

Edit living plans and designs in place under their phase rules. Notify only writers whose paths or criteria change, with current scope, rationale, changed criteria, evidence and next action; keep their handles and completed work. Continue independent writers. Intent edits follow [spec operation](../spec-stage.md#revision-protocol).

For conflicts, inspect both tasks' intent and resolve within their paths in the integration worktree, then continue integration. Discarding work follows the [user gate](../decision-frame.md#user-gate-boundaries). Record unresolved conflicts and retained candidates.

After interruption, use status, inspect recorded launches and integration state, and reconcile live handles before relaunching. A relaunch acknowledges the old writer as stopped; do not run two writers against one worktree. Verification must follow the last relevant edit. Report completion only when criterion evidence is current, required reviews are resolved, and delivery and cleanup are accounted for.

Before report completion, when plan Risk is `med` or `high`, record 3–5 `focus` bullets with evidence; Risk `low` does not require a record.

## Cap-ending SHOULD corrections

Use the exception only for recorded fixes of accepted SHOULD findings from the final completed review round at or above the cap. Run current criterion and contract checks; report each correction as verified but not re-reviewed against the completed review baseline. Accepted MUST fixes require review, pending MUST rejections require confirmation, and unrelated edits need fresh review.

For plan/design corrections, use the existing edit record with before and after canonical hashes and identify the originating SHOULD finding in its rationale. Record the reviewed baseline, correction and verification as a `focus` bullet with an evidence link; the walkthrough renderer places it under Review Focus.

For code corrections, pass review-fix metadata with worktree commit as described in the [toolkit contract](../toolkit.md#worktree-commit). A later source edit outside this exception needs checks and fresh review.
