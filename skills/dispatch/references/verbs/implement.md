# Implement

Resolve the full governing spec and plan, following Parent pins through a design when present. For an objective, author the [spec](../spec-stage.md) and [plan](plan.md) first. When authoring a design, follow the [design guide](design.md); for a supplied design, follow the [ordered increment loop](design.md#implement-an-approved-design) before this single-plan procedure. An assigned child targets its pinned increment plan in its seeded session, not the design route; at each checkpoint or gate return to the parent and wait for continuation. After approval, use this procedure and return the result after uncommitted delivery, report and cleanup. The [toolkit contract](../toolkit.md) owns tool arguments and result shapes.

1. Follow the [scope round](../grounding.md#scope-round) rule. For a design increment whose plan this invocation authors, ground it first under [design increments](../grounding.md#design-increments). Lint the artifacts. Resolve outstanding plan findings and escalations; failed plan-review slots follow [failed-slot coverage](../review-coverage.md#failed-slot-coverage). If this invocation authors the plan, propose its level after lint; record it under [run level](../spec-stage.md#run-level) before the first review. A review or implementation may raise it under the same rule. Run a new plan review only when no completed plan review in the session covers the current spec and plan hashes, or when the user asks; a settled plan from `plan` is not re-reviewed. Bind spec, plan and optional design in the ledger with the applicable user approval tuple.
2. Run baseline checks and retain failures. Choose bounded repairs or reported limitations against governing intent.
3. [Create](../toolkit.md#worktree-create) each ready task worktree, [render its brief](../toolkit.md#brief-render) and launch a native writer there on the `brief render` result. `worktree create` refuses a task until its prerequisites have integrated; verify an integrated prerequisite before creating its dependents. Keep active task writers within `doctor run` `writeConcurrency`. A brief names the governing spec path for a whole read and carries shared plan context, task scope, criteria and checks.
4. Keep each writer running through inspection, discriminating RED tests, implementation to GREEN, refactoring and affected-file verification. Their reply gives status, `reportPath`, a one-line summary and `concerns: <n>`. Read `reportPath` when status is not `DONE`, concerns exceed 0, or integration or verification fails. Missing RED is a review finding. Shortcut-only concerns need recording, not repair or escalation.
5. Inspect the actual delta and evidence. [Submit](../toolkit.md#worktree-submit) the candidate, [integrate](../toolkit.md#worktree-integrate) it and run [criterion and contract verification](../toolkit.md#verify-run) on the integrated tree.
6. Run the [verification step](verify.md) on integration before test cleanup. Commit verifier-added tests and fixes with `worktree commit`; criterion and contract checks must pass on the new HEAD before cleanup. Any verifier-added test launches cleanup, so `<base>..HEAD` includes it.
7. Apply [shared](../templates/quality-bar.md#shared) and [testing](../templates/quality-bar.md#testing) when scoping and adjudicating cleanup; its retention gates match code review's [testing](../templates/quality-bar.md#testing) bar. Run the test cleanup after integrated criterion and contract checks pass and before code review, at every run level. Launch it when `git diff --name-only <base>..HEAD` in the integration worktree names a path declared in any plan criterion `Tests:` field. Otherwise judge each changed path against host test conventions and skip only when none is a test, fixture or helper file; a skip records and commits nothing. To launch, render the [test-cleanup brief](../templates/test-cleanup-brief.md) with the [`brief test-cleanup`](../toolkit.md#brief-test-cleanup) action from a values file holding `base` and `integrationPath`; the action derives `planPath` from the bind record and refuses when no plan is bound. Launch one utility subagent ([routing](../../SKILL.md#routing)) on the `brief test-cleanup` result; it runs only its edited test files. When it reports, check that the report ends with its JSON block, every `removed` ID is a plan criterion and the counts are non-negative integers; then copy the block to `<session>/.state/test-cleanup.json`. Commit with [worktree commit](../toolkit.md#worktree-commit) and `--test-cleanup <session>/.state/test-cleanup.json` whenever `removed` is non-empty or `deleted` or `merged` is non-zero. Use plain `worktree commit` only for `removed: []`, `deleted: 0` and `merged: 0` with rewrite changes; commit nothing when nothing changed. After cleanup commits or skips, start full contract and remaining criterion verification as a background call, retain its handle, and start code review on the same integration HEAD together; wait for both before repairs. A removed criterion keeps its pre-cleanup evidence and is not rerun. If verification fails, repair and commit it on a new HEAD, then rerun checks and review under existing rules.
8. Review code using the [shared](../templates/quality-bar.md#shared), [code](../templates/quality-bar.md#code) and [testing](../templates/quality-bar.md#testing) criteria, including cleanup deletions judged against the retention gates. A green suite cannot detect missing protection; a deletion that removes required protection is a MUST finding whose accepted fix restores or rewrites the test. Resolve MUST findings, rejection confirmations and duplicates under [rulings and fix scope](../review-rules.md#rulings-and-fix-scope); pending or escalated confirmations block delivery and report completion. Apply accepted fixes in integration, commit and rerun criterion and contract checks. Require a completed review with settled [failed-slot coverage](../review-coverage.md#failed-slot-coverage), no open escalations and no unresolved accepted fixes. Route a `coverage-decision` refusal or `user` decision to the user through the [Decision Frame](../decision-frame.md#review-escalation) with a recommendation. Normally it must cover the exact integration HEAD; recorded, verified accepted SHOULD fixes from a final completed round at or above the cap may use the exception in [review rules](../review-rules.md#review-provenance-and-applicability); record and verify them per [worktree commit](../toolkit.md#worktree-commit) and [edit record](../toolkit.md#edit). The exception requires current criterion and contract checks. The no-fix path reuses the exact completed review.
9. Each time all review rounds settle, if accepted review fixes changed proved behaviour, append a `partial` verification record with `open: ["<cycle>:V0"]` before launching one fresh targeted re-check covering those fixes together. Never re-check between rounds or add tests in a re-check; report a test gap as a limit. Route issues through the verification loop; count three fix rounds per issue. A re-check fix needs criterion and contract checks and another code review round; repeat this step when review settles again.
10. After code review and before delivery, inspect every criterion marked `Evidence: review`. Check each declared scenario and status, gather criterion-specific evidence, then present all required user manual-complete decisions with their evidence in one user request. Record each user's decision in the existing user-only [manual record](../toolkit.md#manual-complete) after they respond; keep delivery pending while any required decision is absent. Route missing or failed automated evidence through existing verification and escalation. If no manual decision is pending, continue without a user request.
11. Deliver the exact verified source as unstaged caller changes (no caller commit). Apply [spec layout](../templates/quality-bar.md#spec) to the walkthrough. Complete the [report](../toolkit.md#report-complete) only after delivery; its completion check remains the final evidence check. [Clean](../toolkit.md#worktree-cleanup) owned worktrees. Follow [delivery preconditions and recovery](../toolkit.md#worktree-deliver) for a dirty caller, failure or interruption, and retain the records and work.

Treat scope overrun, concerns, conflicts and red baselines as information with options. Verify each claim, then repair, clarify the plan, retry, retain for recovery or escalate a material user decision. Tool refusals identify an operation prerequisite; inspect the result rather than inventing success or bypassing it.

Edit living plans and designs in place under [revision protocol](../spec-stage.md#revision-protocol). Notify only writers whose paths or criteria change, with current scope, rationale, changed criteria, evidence and next action; keep their handles and completed work. Continue independent writers. Intent edits follow [spec operation](../spec-stage.md#revision-protocol).

For conflicts, follow [continue](../toolkit.md#worktree-continue) or [abort](../toolkit.md#worktree-abort) as applicable. For a stopped writer use [abandon](../toolkit.md#worktree-abandon); to end retained integration use [close](../toolkit.md#worktree-close). Inspect both tasks' intent and resolve within their paths in the integration worktree, then continue integration. Discarding work follows the [user gate](../decision-frame.md#user-gate-boundaries). Record unresolved conflicts and retained candidates.

After interruption, use status, inspect recorded launches and integration state, and reconcile live handles before relaunching. A relaunch acknowledges the old writer as stopped; do not run two writers against one worktree. Verification must follow the last relevant edit. Report completion only when criterion evidence is current, required reviews are resolved, and delivery and cleanup are accounted for.

Before report completion, when plan Risk is `med` or `high`, record 3–5 `focus` bullets with evidence; Risk `low` does not require a record. When writers report shortcuts, record them as focus bullets at any Risk, with the session-relative writer report path as evidence; when bullets would exceed five, group shortcuts in one bullet that keeps each limit and trigger.
