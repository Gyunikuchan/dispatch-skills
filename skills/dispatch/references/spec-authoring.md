# Spec authoring

Spec ground, critique, author and confirm sequence. Read when a verb needs a new spec.

## Resolve and author

Follow a supplied plan or design's Parent pins to the governing spec; an increment plan follows its design. An explicit review spec must agree with settled governing intent. Otherwise reuse the single session spec. Investigate ambiguity before selecting a file.

When a verb needs a new spec, including `review` when no spec exists, use this sequence:

1. **Ground.** Ground the domain under [grounding guidance](grounding.md) before intent refinement. Derive explorer questions from the request. Propose no solution, scope or option before grounding completes.
2. **Critique and refine.** For `plan`, `design`, or an `implement` that authors its plan or design, critique the request against grounded facts before detailed questions; skip it for `review` without a spec. Open the first user exchange (grilling round 1, or Confirm on the short path) with a short restatement of the request and the grounded facts that bear on it: current behavior, what the change touches and verified Surprises. Check four lenses: **problem** (the right problem or a symptom), **approach** (a simpler path or an existing mechanism), **scope** (trim or split independent subsystems), **cost and risk** (dependencies, compatibility and user-gate effects). For problem, scope and cost-and-risk, present an alternative only when it is materially better on the lens and not worse on intent; otherwise state in one line that the premise holds, with the reason. For approach, lay out two or three grounded approaches with trade-offs and one recommendation; drop approaches that work against the user's why or that existing work rules out; when one approach remains, say so and state why the others do not fit. The set includes the simplest approach with a reasonable trade-off worth considering, ranked by the [simplicity order](templates/quality-bar.md#shared), never a strawman or a do-nothing option that fails intent; when the recommended approach is already that option, say so. Give each approach its trade-off, limitation and risk, one short clause each. Recommend the simplest presented approach that meets intent and the simplicity floor; a heavier pick states its reason. Give approaches that differ in what the user sees (CLI output, file layout, UI) a short text sketch each. When the user raises the approach or asks about trade-offs, ask the approach as a grilling question; when the user discusses only outcomes, show it with the recommendation as a stated default the user can override in Confirm. Ask the user only decisions that change scope, behavior or risk and that grounding cannot answer; settle other calls as `(assumption)` entries, never questions, and never ask process steps (artifact paths, layout, recon). Each question put to the user states what its answer changes; this applies to `grilling` rounds and Confirm questions. A material unanswered question still blocks approval. When the request states no why and grounding cannot infer it, ask the why alone as the first grilling round, as one open question with no recommended answer (an override of `grilling`'s per-question recommendation for that one question only); the rest of the frontier, including approach options, follows in the next round. An inferred why becomes an `(assumption)`. When the host provides `grilling`, invoke it by name after grounding at every level, except when the critique leaves no user decision open: run no grilling round then, and Confirm carries the critique result, any approach default, stated and assumed intent and the verb recommendation. Otherwise ask the critique as its first-round premise questions, each with a recommended answer. Use context maps or explorers for facts, not grilling subagents. Continue until no user decision is open; the step 4 exchange replaces grilling's closing shared-understanding confirmation, so ask no separate one. Map its output into the canonical spec as best effort. If `grilling` is unavailable, carry the critique in the Confirm exchange and add no other clarification round.
3. **Author.** Apply the [shared](templates/quality-bar.md#shared) and [spec](templates/quality-bar.md#spec) quality criteria. Write `<session>/<slug>.spec.md` from the full chat, grounding and grilling output. Preserve constraints, alternatives, rejected options and actual user decisions; label inferences as `(assumption)` constraints or put them in Open Questions. For each alternative or approach set you present, record a DEC with `Options`, `Rejected` and the user's actual quote; a delegated default records the Choice tagged `(assumption)` with no user quote, and a Confirm override updates that DEC with the user's actual quote. The user's choice governs; the critique alone never blocks progress. [Lint](toolkit.md#lint-run) the spec and resolve parse errors before downstream authoring. Then self-check, without a subagent: read the spec as its plan author would and sort each gap: answered by chat or grounding (fill in), minor (settle as `(assumption)`), or the user's (ask in Confirm, most important first). Lint again after self-check edits and before Confirm. Preserve an existing canonical spec's path.
4. **Confirm.** In one exchange, present the spec path, stated and assumed intent separately and recommend `plan` or `design` from the scope check. When `grilling` ran, this exchange is its closing shared-understanding confirmation: if the reply opens or changes a decision, resume grilling for that branch, then update the spec and its DECs with the user's actual quotes, lint it and repeat this exchange; record no `edit` or `confirm` until the user accepts the repeated exchange. When `grilling` was unavailable or asked no round, use grounded scope and present the critique, any approach default and the self-check questions in this Confirm exchange. Keep an explicit user verb unless that scope contradicts it; if so, explain and recommend the other verb. If the reply settles a presented alternative in this fallback (an approach default, a self-check answer or a corrected assumption), first update the canonical spec and its DEC with the user's actual quote, then lint the updated spec. If the reply changes intent beyond that or opens a new decision in this fallback, follow the [revision protocol](spec-stage.md#revision-protocol) (for a new decision, resume `grilling` for its branch first when the host provides it), which records the new confirmation; otherwise:

   Record the user's reply as a `confirm` ledger record with the spec hash ([toolkit](toolkit.md#confirm)) once, using the resulting hash if this fallback update ran, or the current spec hash otherwise. In this fallback, the reply is both the decision and confirmation, so add no extra exchange.

Follow the [scope round](grounding.md#scope-round) rule.

Direct other planning skills' output into this canonical owner. Merge stray material before removing it; deleting tracked work follows the user gate.
