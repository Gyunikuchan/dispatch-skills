# Execution Discipline Adoption — High-Level Implementation Specification

**Date:** 2026-09-18
**Updated:** 2026-09-19
**Status:** Approved direction; ready for phased implementation
**Source review:** [obra/superpowers](https://github.com/obra/superpowers) (`main`, MIT, 14 skills) compared with this repository's dispatch, plan-review, code-review, and implementation workflows.

## 1. Context

Superpowers and `implement-dispatch` address the same lifecycle: plan, approve, implement, verify,
review, and settle. Superpowers is stronger at execution-state and judgment discipline: durable
position tracking, explicit implementer outcomes, bounded escalation, red-green TDD, and
evidence-before-claims. This repository is stronger at structural rigor and multi-provider
orchestration: preparation manifests, claim verification, consensus, checkpoints, provider
fallback, and bounded review context.

This specification selectively adopts the execution disciplines that improve correctness or
recovery without weakening host neutrality or making every invocation pay for unnecessary
ceremony.

### Goals

1. Make implementation progress recoverable after compaction or session loss without relying on
   commits or mutable walkthrough prose.
2. Make delegation outcomes actionable by distinguishing success, concern, missing context, and
   genuine blockage.
3. Prevent vacuous tests, unsupported completion claims, retry thrashing, and silent scope growth.
4. Reject structurally unexecutable plans before spending cross-provider review tokens.
5. Reduce follow-up review cost by batching independent fixes while preserving scoped verification.
6. Support milestone decomposition for genuinely large work without replacing the efficient
   single-pass default.
7. Preserve the existing strengths of claim verification, consensus, checkpoints, provider
   fallback, and caller-owned Git state.

### Non-goals

- No automatic commits, branches, worktrees, merges, or pull requests.
- No session-start hooks or automatic invocation of `implement-dispatch`.
- No periodic polling or check-in cadence for background delegates.
- No per-role or per-round `reviewModel` configuration in this work.
- No new `unverifiable` finding class.
- No general rationalization tables without an observed failure that justifies them.
- No requirement to decompose ordinary bounded or mechanical cross-cutting changes.

### Design constraints

- **Evidence over speculation:** behavioral rules require a recorded failure, repository history,
  or an optional pressure test.
- **Low steady-state load:** prefer one-sentence contracts and deterministic scripts over recurring
  prose.
- **Host neutrality:** scripts inspect or route commands; they do not hard-code host-specific test,
  build, or model commands.
- **Single user approval gate:** retain approval after plan settlement and before implementation.
- **Minimal interrogation:** surface only non-obvious, decision-changing questions. `grilling`
  remains user-invoked.
- **Monolithic by default:** phase work only when the decomposition threshold in Phase 5 is met.
- **One-way scope:** scope can increase during a run, but classification and review rigor never
  silently decrease.

The phase numbers in this document are the v0.4 delivery sequence, not the completed phase numbers
from the earlier repository refactor roadmap.

## 2. Target behavior

A completed implementation run has the following observable lifecycle:

1. The orchestrator maps success criteria to planned changes and verification.
2. Plan preparation rejects fatal structural defects and passes warnings to reviewers.
3. The selected host verification commands run after plan settlement and establish a recorded
   baseline before approval.
4. The user approves the settled plan and any default-included recommendations.
5. Each implementation dispatch names an explicit model and returns a typed terminal status.
6. New tests are observed failing for the expected reason before implementation makes them pass.
7. The execution ledger records task completion, non-review rulings, retry attempts, and review
   summaries.
8. Retries follow a three-attempt escalation ladder with root-cause analysis before code changes.
9. Any scope growth triggers reclassification and flow resolution without downgrading rigor.
10. Accepted follow-up fixes are grouped into independent clusters and each cluster is implemented,
    verified, and reviewed once.
11. Final completion claims cite fresh command output; delegate reports alone never establish
    success.
12. Handoff combines execution and review rulings, reports deferred items using stable opt-in keys,
    and preserves the existing artifact relocation behavior.

## 3. Delivery strategy

Implement phases in order. A phase may ship independently once its completion gate passes. Later
phases must build on the public behavior established by earlier phases rather than introducing a
parallel workflow.

| Phase | Outcome | Depends on |
|---|---|---|
| 0 | Core correctness contracts | None |
| 1 | Typed implementation outcomes and bounded escalation | Phase 0 |
| 2 | Durable execution ledger and resume behavior | Phase 1 |
| 3 | Deterministic plan lint | Phase 0 |
| 4 | Keyed opt-ins and clustered follow-up fixes | Phases 1–2 |
| 5 | Architect-phased decomposition | Phases 1–4 |

Phase 3 may start after Phase 0. Phase 2 starts after Phase 1 and may proceed in parallel with any
remaining Phase 3 work when their changes are isolated. Phase 4 may also proceed in parallel with
Phase 3 after Phase 2 settles.

## 4. Phase 0 — Core correctness contracts

### Objective

Strengthen the existing workflow using behavioral and documentation changes only. This phase
introduces no schema or configuration changes.

### Required changes

- In `skills/implement-dispatch/SKILL.md`:
  - After plan settlement and default-scope materialization, create the walkthrough and run each
    selected `Verification Plan / Automated Tests` baseline command once before presenting the
    approval gate.
  - Create the walkthrough before baseline verification whether code review is enabled or disabled.
  - Record each command, exit status, and concise output evidence under walkthrough
    `## Verification & Validation`.
  - If the baseline is red, require a user ruling between proceeding with a known-red baseline and
    fixing the baseline first. `Fix first` amends and re-reviews the plan to include the repair; it
    does not authorize production-code writes before approval. An unavailable command is recorded
    explicitly and cannot be described as green.
  - Require every new test to be run and observed failing for the expected reason before production
    implementation. A test that passes on arrival does not satisfy the gate.
  - Re-run flow resolution after any mid-run scope growth. Preserve explicit levels and never
    downgrade an automatically resolved level.
  - Require fresh verification output for every final completion claim.
- In `skills/dispatch/references/alignment.md`:
  - State that delegate success reports are claims, not verification.
  - Reject findings that add unused capability or contradict user-approved decisions.
  - Require related unclear findings to be clarified before any of them are applied.
- In `skills/dispatch/SKILL.md`, `skills/dispatch-plan-review/SKILL.md`, and
  `skills/dispatch-code-review/SKILL.md`:
  - Treat a child without a terminal outcome after the runner's `--timeout` as a runner failure.
  - Route that failure through the existing native-fallback contract.
  - Keep notification-driven waiting; add no polling loop.

### Completion gate

- Baseline verification, final evidence, scope re-resolution, and timeout fallback each have one
  authoritative rule across the affected skills.
- Baseline-red behavior has an explicit user decision point and cannot be reported as green.
- Code-review-disabled runs still preserve baseline evidence in the walkthrough.
- Final handoff requires fresh host command evidence.
- Timeout without a terminal outcome deterministically enters native fallback.
- Documentation and existing skill-validation tests pass without new schema expectations.

## 5. Phase 1 — Typed outcomes and bounded escalation

### Objective

Replace binary delegate success/failure handling with statuses that determine the next legal
action, then cap retries so changing errors cannot cause indefinite thrashing.

### Status contract

Every implementation delegate returns exactly one terminal status:

| Status | Meaning | Required orchestrator action |
|---|---|---|
| `DONE` | Requested scope completed without known concerns | Verify independently |
| `DONE_WITH_CONCERNS` | Scope completed with material caveats | Read and resolve concerns before verification |
| `NEEDS_CONTEXT` | Work cannot continue with the supplied information | Supply missing context and resume the same session; a replacement consumes the next attempt |
| `BLOCKED` | Context, capability, architecture, or task size must change | Change the blocking condition before retrying |

Implementation dispatches always pass an explicit model. Omission must not inherit the
orchestrator's potentially more expensive model. Phase 1 deliberately tightens configuration
compatibility: every platform routable for implementation must resolve a model. Update the sample
configuration for every supported host and document migration for existing configurations. A
missing model stops preflight with a stable diagnostic naming
`implementation.platforms.<platform>.model`; review-only configuration remains valid.

An attempt is one launched implementation delegate for one task or fix cluster. Missing or
malformed terminal status, delegate or runner failure, `BLOCKED`, or red independent verification
consumes that attempt. `NEEDS_CONTEXT` pauses the current attempt only when the same delegate
session can resume; launching a replacement delegate consumes the next attempt.
`DONE_WITH_CONCERNS` requires an orchestrator ruling before independent verification. No task or
cluster may launch more than three implementation delegates, and failed delegated work never
transfers silently to the orchestrator. The counter resets only when an approved scope change
creates a new task or cluster.

### Escalation ladder

1. **Attempt 1:** primary delegate implements test-first.
2. **Attempt 2:** same delegate receives the recorded failure evidence and the instruction to
   identify root cause before modifying code.
3. **Attempt 3:** the same native implementation platform uses the next higher configured
   implementation level that resolves to a distinct model or effort, carrying the failure history
   and root-cause analysis.
4. **Termination:** any failure after Attempt 3 stops the run and records a stable failure for user
   ruling, even if the error changed between attempts.

Implementation escalation uses the existing ordered levels
`low → medium → high → xhigh → max`. Starting above the effective level, select the first configured
level whose resolved model or effort differs from Attempt 2. If none exists, stop after Attempt 2
and record that escalation is unavailable; implementation never crosses to a reserve provider.
Routing uses effective configuration and does not hard-code model names. Flat implementation
entries intentionally resolve identically at every level and therefore provide no escalation tier;
the workflow must not synthesize one. This native-only rule supersedes the source comparison's Q3
proposal to fall back to a reserve provider because reserve candidates are review-only and do not
carry native write authority.

`NEEDS_CONTEXT` does not authorize the orchestrator to take over silently. `BLOCKED` does not
authorize an identical retry.

### Integration surfaces

- `skills/implement-dispatch/SKILL.md`: status handling, explicit-model rule, escalation lifecycle,
  terminal failure behavior, and replacement of the existing two-identical-failures rule.
- `skills/implement-dispatch/scripts/resolve-flow.mjs`: expose the next distinct configured
  implementation level or an explicit exhausted result.
- `skills/implement-dispatch/config.sample.jsonc`: clarify that implementation level order is the
  escalation order; add no new configuration key.
- `tests/skills/implement-dispatch/resolve-flow.test.mjs` and
  `tests/skills/implement-dispatch/resolve-flow-cli.test.mjs`: cover level stepping, skipped
  equivalent levels, missing effective models, and exhaustion.

### Completion gate

- All four statuses map to one unambiguous next action.
- Tests demonstrate Attempt 3 chooses the next distinct configured implementation level without
  hard-coded model identifiers.
- Transition tests cover every status plus missing or malformed status, runner failure, and red
  verification after `DONE`.
- A fourth implementation attempt is impossible within the documented workflow.
- The existing two-identical-failures rule is removed; the three-attempt ladder is authoritative.
- Flow resolution stops with a configuration diagnostic before implementation when the effective
  implementation entry has no model.
- Every launched implementation dispatch includes that explicit resolved model.
- Stable failure preserves evidence needed for a user ruling.

## 6. Phase 2 — Durable execution ledger and rulings

### Objective

Persist execution position independently of walkthrough freshness so a compacted or fresh
orchestrator can reconstruct completed work before dispatching again.

### Ledger identity and location

`resolve-artifact-paths.mjs` adds an additive `ledgerPath` field:

```text
<os.tmpdir()>/dispatch-skills/<repo-hash>/<slug>-ledger.md
```

`<repo-hash>` is the first 12 lowercase hexadecimal characters of SHA-256 over the canonical
absolute result of `git rev-parse --show-toplevel`. The local root, rather than the remote URL,
keeps resolution offline and isolates worktrees.

The ledger is append-only, is not a review artifact, is not relocated at handoff, and does not
participate in plan or walkthrough freshness. Its dedicated `dispatch-skills/` namespace is
intentional: unlike ephemeral runner logs and prompt spills, the ledger must remain available for
resume until the OS purges it.

`<slug>` is the canonical plan slug. A resumable implementation requires an explicit or
branch-derived slug. When initial artifact resolution reports `slugSource: "conversation"` or no
slug, the orchestrator chooses and persists an explicit slug at that step, before authoring the
plan, so the plan, walkthrough, and ledger share one canonical identity.

The ledger is segmented by append-only `run-start` and `run-complete` events. `run-start` records a
run ID, canonical plan content hash, root slug, and baseline worktree fingerprint. Resume considers
only the latest unterminated segment whose plan hash matches; a completed or mismatched segment is
never resumed implicitly.

### Event grammar

Each event occupies one markdown list item:

```markdown
- task: 1 paths: [src/foo.ts] status: complete diff: <hash>
- ruling: <decision> — <reason> — <cost if wrong>
- fix-attempt: 1 target: claude:0 status: BLOCKED reason: <diagnostic>
- review: code R1 verified: <k> rejected: <m> disputed: <n>
```

Task events use changed paths and a deterministic diff hash rather than commit IDs because Git
mutation remains caller-owned. The hash is SHA-256 over a canonical patch for the sorted task path
set relative to the segment's recorded baseline, including staged, unstaged, untracked, deleted,
renamed, and mode-change state. Non-review decisions made during implementation are recorded as
`ruling:` events. Review decisions remain in existing plan and walkthrough resolution logs.

### Resume behavior

Before any dispatch after compaction or in a fresh session:

1. Resolve the deterministic ledger path.
2. Read all valid ledger events.
3. Compare recorded paths and diff hashes with current `git status` and diff.
4. Reconstruct completed tasks, active task, retry count, and unresolved rulings.
5. Dispatch only work not proven complete by both ledger and working tree evidence.

Hash drift enters `needs-reconciliation`; it does not automatically redispatch a task when a later
ledger event owns any of the same paths. Reconciliation must attribute the live diff before work
continues.

If the OS purged the ledger, reconstruct best-effort state from the working tree and walkthrough.
The absence of a ledger is recoverable and must not produce a success-shaped assumption.

### Integration surfaces

- `skills/dispatch/scripts/resolve-artifact-paths.mjs`: canonical root hashing and `ledgerPath`
  output.
- `tests/skills/dispatch/resolve-artifact-paths.test.mjs`: deterministic paths, lowercase
  12-character hash, worktree isolation, OS-path handling, and rejection of conversation-derived
  slugs for resumable implementation.
- `skills/implement-dispatch/SKILL.md`: append points, resume sequence, and handoff merge.
- A focused ledger helper under `skills/implement-dispatch/scripts/` if parsing and append
  validation would otherwise be duplicated. Helper extraction and naming remain implementation
  discretion; the event and resume contracts above are mandatory.
- Focused tests under `tests/skills/implement-dispatch/` for event validation, append behavior,
  state reconstruction, drift, and missing-ledger fallback.

### Completion gate

- The same canonical repository root and slug always resolve to the same ledger path.
- Different worktree roots resolve to different paths.
- A protected-branch or detached-HEAD run establishes an explicit slug before implementation
  rather than treating a conversation-derived slug as resumable.
- A simulated interrupted run resumes without redispatching a task whose ledger entry and current
  diff agree.
- Completed or plan-mismatched segments and reused slugs are not resumed implicitly.
- Tests cover untracked files, deletions, renames, overlapping task paths, and a mismatched diff
  entering reconciliation rather than automatic redispatch.
- Handoff emits one `Rulings made` list combining ledger rulings with review resolution-log
  rulings.

## 7. Phase 3 — Deterministic plan lint

### Objective

Stop structurally unexecutable plans before cross-provider review while preserving reviewers'
responsibility for semantic judgment.

### Validation rules

Blocking defects return:

```json
{
  "schemaVersion": 1,
  "kind": "plan",
  "action": "<preparation-action>",
  "status": "decision-required",
  "decision": "plan-lint",
  "artifact": { "canonicalPath": "<path>", "tier": "<tier>", "slug": "<slug>" },
  "freshness": { "status": "<status>", "changedSections": [] },
  "defects": [{ "rule": "<rule-id>", "locus": "<section-or-line>", "message": "<diagnostic>" }],
  "cleanupPaths": []
}
```

`plan-lint` has no `choices` and is never replayed as a request `decision`. In orchestrated mode,
the orchestrator fixes its in-run plan and prepares again. Standalone mode stops with the
diagnostics so the plan owner can edit and rerun. `defects` is the only additive field on the
existing `decision-required` manifest envelope.

Blocking rules:

- The same path has conflicting `[NEW]` and `[DELETE]` actions.
- The plan has no literal `## Verification Plan` section or no fenced/backticked command under
  `### Automated Tests`.
- A present `## Success Criteria` item lacks both a syntactic `Changes:` path reference and
  `Verify:` command.

Add `## Success Criteria` to the canonical plan template. Each item has a stable criterion ID and
at least one machine-readable mapping:

```markdown
- [SC1] <criterion>
  - Changes: <relative-path>[, <relative-path>...]
  - Verify: `<command>`
```

At least one of `Changes:` or `Verify:` is required per criterion. The linter checks references,
not whether the named change or command is semantically sufficient.

Non-blocking warnings are included in reviewer prompt context:

- no `## Success Criteria` section in a legacy plan;
- `TODO`
- `TBD`
- `implement later`
- `fill in`

The linter checks structure and command presence only. It never executes verification or attempts
to determine whether a command is correct for the host.

### Integration surfaces

- `skills/dispatch-plan-review/scripts/prepare-review.mjs`: invoke lint after reading the canonical
  artifact and before creating dispatch files.
- `skills/dispatch-plan-review/references/plan-template.md`: add the structured
  `## Success Criteria` section.
- A pure lint helper beside `prepare-review.mjs` if needed for focused unit tests.
- `tests/skills/dispatch-plan-review/prepare-review.test.mjs`: one case per blocking defect,
  warnings in prompt context, clean plan behavior, and false-positive boundaries for fenced code.
- `skills/dispatch-plan-review/SKILL.md`: document blocking and warning outcomes.

### Completion gate

- Every blocking rule returns `decision-required` before prompt, batch, or dispatch files are
  created.
- Lint blockers return `decision: "plan-lint"` with structured defects, no choices, and cannot be
  replayed as a request decision.
- Warning-only plans remain `ready` and every warning is visible to all review targets.
- Canonical fixtures are upgraded to the new template and remain `ready`; legacy fixtures without
  `## Success Criteria` remain `ready` with a warning. Legacy plans missing required verification
  structure return `decision-required / plan-lint` without creating review files.
- Tests prove that the linter detects syntax, not host semantics.

## 8. Phase 4 — Keyed opt-ins and clustered follow-up fixes

### Objective

Make deferred decisions easy to toggle and reduce review cycles by processing independent accepted
fixes as clusters instead of one finding at a time.

### User-facing opt-ins

At plan approval and handoff, render two distinct sections when decision-changing items exist:

```markdown
### Recommended Follow-ups (Default: Included)
- [R1] [x] Fix type cast in foo.ts — addresses the reviewed edge case.

### Out-of-Scope / Adjacent Items (Default: Excluded)
- [O1] [ ] Add telemetry metrics — deferred to a separate change.
```

- `SHOULD` and consider items default to included unless the orchestrator records a one-line reason
  to exclude them.
- `adjacent` and other out-of-scope items default to excluded.
- Keys are stable within the approval or handoff interaction and support replies such as
  `exclude R2, include O1`.
- When no items exist, state `none` without asking a question.
- Review finding IDs remain authoritative in resolution logs; `[R#]` and `[O#]` are interaction
  aliases, not replacements.
- Before approval, materialize default-included recommendations into proposed changes, success
  criteria, and verification mappings, then rerun lint, flow resolution, and any required plan
  review. A toggle that changes executable scope keeps the same logical approval gate open but
  repeats settlement before approval is accepted.
- At handoff, a non-empty opt-in set requires an explicit response; accepting the defaults is a
  response, not silence. Including an `O#` item triggers the one-way scope rule.

### Cluster behavior

1. Group findings only when their affected path sets are pairwise disjoint and they have no
   declared ordering, interface, or verification dependency. Keep same-file findings separate;
   when dependency is uncertain, keep the findings separate.
2. Dispatch one implementation task per cluster.
3. Run the deduplicated union of every member finding's required verification commands, then one
   scoped review loop per cluster; every command must pass.
4. If a cluster fails, retain the current working tree, preserve completed clusters, and split only
   the failed cluster into smaller independently provable groups. Attribute and reverify partial
   outcomes before redispatching remaining work.
5. Apply the Phase 1 escalation ladder within each cluster.

### Integration surfaces

- `skills/implement-dispatch/SKILL.md`: approval, handoff rendering, response application, and
  cluster lifecycle.
- `skills/dispatch-code-review/SKILL.md`: standalone accepted-fix clustering and unbundling.
- `skills/dispatch/references/alignment.md`: interaction aliases and their relationship to stable
  finding IDs.
- Existing consensus, rebuttal, and preparation scripts remain the source of truth for review
  settlement.

### Completion gate

- Recommended and out-of-scope items have distinct defaults and stable aliases.
- No prompt is emitted when both sets are empty.
- Independent fixes produce one dispatch, verification, and scoped review per cluster.
- A failed cluster can be split without repeating successful cluster work.
- Tests cover disjoint paths with a shared dependency, multiple verification commands, and one
  failed item inside a multi-item cluster.
- Resolution logs retain original finding IDs and final disposition.

## 9. Phase 5 — Architect-phased decomposition

### Objective

Support large changes as milestone sub-plans while keeping standard work on the existing
single-pass path.

### Activation threshold

Decomposition is permitted only when at least one condition is demonstrated:

1. **Strict sequential primitives:** later work cannot be implemented, compiled, or verified until
   an earlier foundation exists.
2. **Disjoint verification boundaries:** milestones target separate subsystems with distinct verify
   commands or build targets, and joint execution creates an unmanageable blast radius.
3. **Context ceiling:** the combined specification, expected diff, and test payload contains about
   8–10 or more distinct functional deliverables.

File count alone, a mechanical API migration, or ordinary cross-cutting edits do not meet the
threshold.

### Root plan contract

When activated, the orchestrator authors an Architect Roadmap / Root Plan at
`.scratch/plan/<yyyy-mm-dd>-<slug>-root-plan.md` that contains:

- system goals and non-goals;
- architecture and domain invariants;
- milestone order and dependency edges;
- milestone scope, success criteria, and verify command;
- shared interfaces and ownership boundaries;
- integration and final verification requirements.

Each milestone is a scoped `implement-dispatch` run with its own plan settlement, implementation,
verification, review, and checkpoint. The reviewed root plan is the sole user approval gate for a
phased run. Milestones use a scoped phased-execution mode and reuse that approval while their scope
remains fully contained in the root plan. A decision-changing deviation pauses dependent work,
updates and re-reviews the root plan, and requires an explicit user ruling before additional
writes. Every milestone implementer and reviewer receives the root plan as read-only background
context. Milestone completion is recorded in the Phase 2 ledger.

Milestones have stable IDs and deterministic paths such as
`.scratch/plan/<yyyy-mm-dd>-<root-slug>-mNN-<milestone-slug>.md`. One root-run ledger keyed by the
root slug records milestone start, completion, invalidation, and integration completion. Root and
milestone plans and walkthroughs remain available through final integration; handoff passes every
active artifact to the existing relocation utility and reports every destination. The ledger is
never relocated.

The final integration milestone verifies cross-milestone behavior and cannot be replaced by the
sum of individual milestone checks.

### Integration surfaces

- `skills/implement-dispatch/SKILL.md`: activation decision, root-plan lifecycle, milestone loop,
  and final integration gate.
- `skills/dispatch/scripts/resolve-artifact-paths.mjs`: add an additive `rootPlan` artifact kind
  using the canonical path above.
- `.agents/AGENTS.md`: extend the scratch allowlist with active root plans.
- Plan templates or references: root-plan headings and milestone contract.
- Plan-review preparation: attach the root plan as bounded context for milestone reviews.
- Code-review preparation: attach the root plan as bounded context for milestone reviews.
- Ledger events: milestone start, completion, and invalidation.

### Completion gate

- A bounded ordinary change still follows one `implement-dispatch` run.
- An eligible large fixture produces a root plan with ordered, independently verifiable
  milestones.
- Every milestone prompt includes bounded root-plan context.
- A failed milestone blocks dependents without invalidating independent completed milestones.
- Final completion requires the integration milestone's fresh verification evidence.
- Root and milestone artifacts have deterministic ownership and all are reported at relocation.

## 10. Cross-phase validation and rollout

For each phase:

1. Add or update focused Node tests for changed scripts.
2. Run the narrowest affected test files with
   `node --test tests/skills/<area>/<file>.test.mjs`.
3. Run `npm run validate:configs` when configuration parsing or examples are touched.
4. Run `npm run hashes` after all shipped-file edits.
5. Run `npm test` last.
6. Pressure-test new behavioral rules optionally using RED → GREEN → REFACTOR; retain the transcript
   only when it reveals a material failure mode or closes a loophole.

Roll out one phase at a time. A phase is complete only when its completion gate is met and its
documentation matches executable behavior. Do not land Phase 5 as prose-only behavior if the
required root-plan propagation cannot be verified.

## 11. Decision records

These decisions are settled context for implementation. Reopening one requires new evidence or an
explicit user decision.

`P#` and `N#` are proposal identifiers from the source comparison, not implementation phase
numbers.

| ID | Decision | Rationale |
|---|---|---|
| ADR-1 / P1 | Store the execution ledger in OS temp at a deterministic repo-hash path | Survives compaction without changing `.scratch/`; isolates worktrees and stays offline |
| ADR-2 / P1 | Key task completion to paths and diff hash, not commits | Git mutation is caller-owned and mid-run commits may not exist |
| ADR-3 / P1 | Keep ledger separate from walkthrough and do not review or relocate it | Execution position is not artifact description; mixing them creates false freshness drift |
| ADR-4 / P2 | Use two keyed opt-in sections with recommended items included and adjacent items excluded | Clear defaults and low-friction user toggling |
| ADR-5 / P2 | Log non-review rulings in the ledger and review rulings in resolution logs | Preserves the existing authoritative review history while making runtime choices recoverable |
| ADR-6 / P3 | Cap implementation at three attempts and require root-cause analysis before Attempt 2 changes | Prevents identical-error and error-mutation thrashing |
| ADR-7 / P3 | Escalate through distinct configured levels on the native implementation platform; supersede source comparison Q3 reserve fallback | Uses the existing host-neutral configuration without granting review reserves native write authority |
| ADR-8 / P4 | Treat timeout without terminal outcome as runner failure and use native fallback | Host notifications make periodic polling redundant |
| ADR-9 / P5 | Require fresh command evidence for completion claims | Delegate reports are untrusted claims |
| ADR-10 / P6 | Require explicit models for implementation dispatch only; defer a review-model matrix | Prevents accidental expensive inheritance without adding a new configuration surface |
| ADR-11 / P7 | Batch accepted fixes by independence cluster | Avoids up to `N - 1` redundant review cycles while containing failures |
| ADR-12 / P8 | Require observed red before green for new tests | Prevents vacuous tests that pass without exercising new behavior |
| ADR-13 / P9 | Make structural lint blocking and placeholder lint advisory | Stops unexecutable plans without letting heuristics create false blockers |
| ADR-14 / P10 | Verify once before implementation and disclose a red baseline at approval | Separates pre-existing failure from implementation regression |
| ADR-15 / P13 | Re-resolve on scope growth and never downgrade | Keeps review rigor aligned with the largest observed scope |
| ADR-16 / P14 | Keep monolithic execution as default; phase only above a high threshold | Protects token efficiency and avoids unnecessary orchestration |
| ADR-17 / N3 | Reject unused capability and decision-conflicting findings; clarify related ambiguity first | Prevents review from expanding approved scope through speculation |
| ADR-18 / N4 | Keep behavioral pressure testing optional repository tooling | Provides evidence without adding cost to normal workflow |
| ADR-19 / N1 | Require one of four typed terminal implementation statuses | Binary success/failure loses the information needed for context repair, concern rulings, and escalation |

### Deferred decisions

- A per-role/per-round `reviewModel` matrix awaits round-cost data and explicit interface approval.
- Rationalization or drift tables await an observed excuse captured by pressure testing or a real
  transcript.
- An `unverifiable` finding class remains deferred because `adjacent` and `## Follow-ups` cover the
  current need.

### Dropped proposals

- Plan self-review ritual: no observed placeholder or inconsistency failures; deterministic lint
  covers the inexpensive part.
- Standalone three-fix architecture breaker: absorbed by the escalation ladder's terminal ceiling
  and root-cause requirement.
