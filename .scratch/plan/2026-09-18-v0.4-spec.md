**Date:** 2026-09-18
**Updated:** 2026-09-20
**Status:** Phase 0 complete; Phases 1–5 remain approved for phased implementation (implementers read §§1–10; §11 is settled decisions; review history: `2026-09-18-v0.4-spec-review-log.md`)
**History:** [2026-09-18-v0.4-spec-review-log.md](./2026-09-18-v0.4-spec-review-log.md)

## 1. Context

Superpowers is stronger at execution-state and judgment discipline; this repository is stronger at
structural rigor and multi-provider orchestration. This specification adopts only the execution
disciplines that improve correctness or recovery, without weakening host neutrality or adding
per-invocation ceremony.

### Goals

1. Make implementation progress recoverable after compaction or session loss without relying on
   commits or mutable walkthrough prose.
2. Make delegation outcomes actionable by distinguishing success, concern, missing context, and
   genuine blockage.
3. Prevent vacuous tests, unsupported completion claims, retry thrashing, and silent scope growth.
4. Reject structurally unexecutable plans before spending cross-provider review tokens.
5. Reduce follow-up review cost by clustering independent fixes while preserving scoped verification.
6. Support technical-design-driven incremental execution for genuinely large work without
   replacing the efficient single-increment default.
7. Preserve the existing strengths of claim verification, consensus, checkpoints, provider
   fallback, and caller-owned Git state.

### Non-goals

- No automatic commits, branches, worktrees, merges, or pull requests.
- No session-start hooks or automatic invocation of `implement-dispatch`.
- No periodic polling or check-in cadence for background delegates.
- No per-role or per-round `reviewModel` configuration in this work.
- No new `unverifiable` finding class.
- No general rationalization tables without an observed failure that justifies them.
- No requirement to decompose ordinary bounded or mechanical cross-cutting changes.
- No concurrent increment implementation, worktree orchestration, or branch-stack management.

### Design constraints

- **Evidence over speculation:** behavioral rules require a recorded failure, repository history,
  or an optional pressure test.
- **Low steady-state load:** prefer one-sentence contracts and deterministic scripts over recurring
  prose.
- **Host neutrality:** scripts inspect or route commands; they do not hard-code host-specific test,
  build, or model commands.
- **One governing approval gate:** ordinary runs approve the settled plan; phased runs approve the
  settled technical-design revision and do not add routine per-increment approval gates.
  Design-changing amendments require approval of the replacement revision.
- **Minimal interrogation:** surface only non-obvious, decision-changing questions. `grilling`
  remains user-invoked.
- **Single-increment by default:** use technical-design-driven decomposition only when Phase 5's
  evidence-based activation rule is met or the user explicitly requests it.
- **One-way scope:** scope can increase during a run, but classification and review rigor never
  silently decrease.

The phase numbers in this document are the v0.4 delivery sequence, not the completed phase numbers
from the earlier repository refactor roadmap.

## 2. Target behavior

After all phases ship, a completed implementation run has the following observable lifecycle; the
tag names the phase that introduces each item:

1. (P3) The orchestrator maps structured success criteria to planned changes and verification.
2. (P3) Plan preparation rejects fatal structural defects and passes warnings to reviewers.
3. (P0) The selected host verification commands run after plan settlement and establish a
   recorded baseline before approval.
4. (P0; P4 recommendations; P5 design) The user approves the settled plan for ordinary work or the
   settled technical design for phased work, including any default-included recommendations.
5. (P1) Each implementation dispatch names an explicit model and returns a typed terminal status.
6. (P0) New tests are observed failing for the expected reason before implementation makes them
   pass.
7. (P2) The execution ledger records task completion, non-review rulings, retry attempts, and
   review round counts with checkpoint references.
8. (P1) Retries follow a three-attempt escalation ladder with root-cause analysis before code
   changes.
9. (P0) Any scope growth triggers reclassification and flow resolution without downgrading rigor.
10. (P4) Accepted follow-up fixes are grouped into independent clusters and each cluster is
    implemented, verified, and reviewed once.
11. (P0) Final completion claims cite fresh command output; delegate reports alone never establish
    success.
12. (P2 rulings; P4 keys) Handoff combines execution and review rulings, reports deferred items
    using stable opt-in keys, and preserves the existing artifact relocation behavior.
13. (P5) Large work uses an approved technical design, one implementation increment per
    invocation, durable resume state, and a separate final integration gate.

## 3. Delivery strategy

Implement phases in order. A phase may ship independently once its completion gate passes. Later
phases must build on the public behavior established by earlier phases rather than introducing a
parallel workflow.

| Phase | Outcome | Depends on |
|---|---|---|
| 0 | Core correctness contracts | None |
| 1 | Typed implementation outcomes and bounded escalation | Phase 0 |
| 2 | Durable execution ledger and resume behavior | Phases 0–1 |
| 3 | Deterministic plan lint | Phase 0 |
| 4 | Keyed opt-ins and clustered follow-up fixes | Phases 1–3 |
| 5A | Technical-design authoring, review, approval, and artifact foundations | Phases 1–4 |
| 5B | Increment execution, amendments, and final integration | Phase 5A |

Phase 3 may start after Phase 0. Phase 2 starts after Phase 1 and may proceed in parallel with any
remaining Phase 3 work when their changes are isolated. Phase 4 starts only after Phases 1–3
settle because its scope materialization depends on Phase 3's success-criteria structure and
linter.

### Verification evidence contract

Every command extracted from the settled plan's `Verification Plan / Automated Tests` is selected
for baseline and final verification; no other command is in scope. A selected command is skipped
only when unavailable or deselected by an explicit, recorded user ruling.
An unavailable or skipped command is recorded with its reason and never counts as passing.
Verification evidence is fresh only when it was produced after the last mutation to any path in
the command's mapped scope and after the last accepted fix or scope materialization affecting that
scope. The approved implementation path set is the union of the paths named by the settled plan's
`[NEW]`/`[MODIFY]`/`[DELETE]` change headings. When no change heading parses (for example a
native-tier plan), the approved path set is every tracked and non-ignored untracked path outside
`.scratch/`, and the walkthrough records that fallback. Before Phase 3, every selected command maps
conservatively to the entire approved path set. From Phase 3, mapping is per command: a command
referenced by `Verify:` (exact trimmed-string match against the extracted commands) only from criteria that all carry `Changes:` maps to the union of those
paths; any other command maps to the entire approved path set. Final completion reruns the
settled command set under this rule.

A plan-level `- None: <reason>` automated-test item is recorded at baseline time under
`## Verification & Validation` as `unavailable` with the plan's reason and never counts as passing.

Baseline and later verification classify each selected command as exactly one of:

- `pass`: exit zero under the settled command contract;
- `accepted-baseline-equivalent`: nonzero, but the normalized failure identity is unchanged from a
  user-accepted red baseline; or
- `regression`: a new failure, a changed failure identity, or a previously passing command that is
  now nonzero.

The baseline record stores command, exit status, failing test/check identifiers when available,
and a bounded normalized diagnostic with volatile timestamps, durations, and temporary paths
removed. Equality requires the same exit status and the same stable identifiers; when identifiers
are unavailable, exact normalized diagnostics are required. An accepted-baseline-equivalent result
does not consume an implementation attempt and is eligible for completion, but every completion
and handoff must label the command `known red — unchanged`, cite the user's ruling, and must not
describe verification as green. A regression consumes the current attempt under Phase 1; until
Phase 1 ships, it counts toward the existing two-identical-failures stop.

Before approval, the workflow may create or update only governing artifacts, walkthrough evidence,
and OS-temp workflow state. Capture repository state before each baseline command and compare it
afterward. Phase 0 captures sorted `git status --porcelain=v1 -z --untracked-files=all` records
plus `git hash-object --no-filters` IDs of the dirty paths that exist in the working tree (deleted
paths record the literal `absent` instead; change detection only, so Git object IDs suffice here).
The parser consumes both NUL-delimited paths of a rename or copy record (`R`/`C`) and records
both; Phase 0 treats any captured delta as a side effect and does not attribute renames.
Phase 2's raw-byte fingerprint contract replaces this capture. Outside a Git work tree, record
`side-effect capture unavailable` and require a user ruling before approval: `proceed without
side-effect capture` (recorded under `## Verification & Validation`) or `abort`.

A baseline command must leave no tracked-file mutation or new non-ignored file inside the approved
implementation path set before approval. Any such side effect enters reconciliation: the workflow attributes it,
stops, and asks the user either to remove it outside the workflow or to amend and re-review the plan
for later reproduction after approval. The workflow never removes caller-owned changes
automatically, and merely classifying a side effect as future scope does not permit the mutation to
remain at the approval boundary. Incidental files outside the approved implementation path set are recorded and
must be proven irrelevant or reconciled before approval. Production-source changes remain
approval-gated.

Observed red is mandatory for a new test intended to prove new or corrected behavior. A
characterization test for already-supported behavior, a test-only repair, or a generated/snapshot
update may proceed without artificial failure only when the walkthrough records the exception,
the evidence establishing the category, and an orchestrator ruling. Adding a test after its
production behavior was already written is not an exception; it records a missed gate and requires
user acceptance before completion.

Until Phase 1 ships, a "task" is the whole approved plan (one implementation launch) and the
existing two-identical-failures stop is the attempt bound for everything below.

The RED gate is a host-observed stage boundary, not a delegate claim. A task requires the split
when any settled success criterion (or, without criteria, the plan's stated intent) requires new
or corrected behavior; otherwise the split is skipped and the exception rules above apply. At
baseline time the orchestrator classifies each approved path as test/test support or production,
using the host's own conventions, and records the split under `## Verification & Validation`; a
path created later is classified under the same recorded rule. In Phase 0, the first
implementation launch for such a task may change test/test-support paths only
and then stops; the host treats any return from that launch as the end of the tests-only stage,
runs the mapped command, records the expected failure identity (under `## Verification &
Validation` until Phase 2; from Phase 2 as a `verification` event with `result: "red"`), and starts
a production continuation only after valid RED. A tests-only launch that cannot reach RED returns
`COMPLETE` with `NEEDS_CONTEXT` or `BLOCKED`; resuming it re-enters the tests-only stage under the
same attempt and its single context-only continuation, and it never yields a `red` verification. Once Phase 1 ships, the tests-only result uses the
typed `RED_READY` stage and may resume the same implementation session when the host supports
a stable handle. Without a resumable handle, a tests-only launch that reaches valid RED is not an
attempt: it and its production continuation share one attempt number. Each task allows at most one
such tests-only launch in addition to its attempts. A test that fails for an unrelated reason
consumes the attempt (before Phase 1: counts toward the two-identical-failures stop) and is not
observed RED. A tests-only launch that mutates any path classified production is likewise
not valid RED and consumes the attempt. An invalid-RED tests-only launch is Attempt 1 (or the
current attempt number); the next launch takes the following number. Recorded exceptions skip this split
only for the categories above. For `self` targets, the orchestrator writes tests only, runs the
mapped command, and records RED before any production edit.

## 5. Phase 1 — Typed outcomes and bounded escalation

### Objective

Replace binary delegate success/failure handling with statuses that determine the next legal
action, then cap retries so changing errors cannot cause indefinite thrashing.

### Status contract

Every implementation delegate returns exactly one terminal status:

| Status | Meaning | Required orchestrator action |
|---|---|---|
| `DONE` | Requested scope completed without known concerns | Verify independently |
| `DONE_WITH_CONCERNS` | Scope completed with material caveats | Read and resolve concerns before verification |
| `NEEDS_CONTEXT` | Work cannot continue with the supplied information | Resumable: one context-only continuation within the attempt; otherwise the attempt is consumed (`self`: see below) |
| `BLOCKED` | Context, capability, architecture, or task size must change | Change the blocking condition before retrying |

The final delegate message contains exactly one machine-readable terminal envelope:

```json
{
  "schemaVersion": 1,
  "status": "DONE|DONE_WITH_CONCERNS|NEEDS_CONTEXT|BLOCKED",
  "stage": "RED_READY|COMPLETE",
  "summary": "non-empty string",
  "evidence": ["bounded path, command, or diagnostic"],
  "concerns": ["required when status is DONE_WITH_CONCERNS"],
  "missingContext": ["required when status is NEEDS_CONTEXT"],
  "blockers": ["required when status is BLOCKED"]
}
```

`stage` is orthogonal to status: `RED_READY` means the scoped test-only change is complete and
the host must run the RED gate before production continuation; `COMPLETE` means the launch is
terminal for its assigned stage (with `DONE`/`DONE_WITH_CONCERNS`, the implementation scope is
finished). Legal pairs: `RED_READY` with `DONE` or `DONE_WITH_CONCERNS`; `COMPLETE` with all four
statuses. `stage` is required on every envelope. `concerns`, `missingContext`, and `blockers`
are non-empty when their status requires them and otherwise omitted or `[]`. `evidence` is always
present; it is non-empty for `DONE`/`DONE_WITH_CONCERNS` and may be `[]` otherwise.
The envelope is either the whole final message as raw JSON or exactly one ```` ```json ```` fenced
block within it; surrounding prose is ignored. The parser rejects prose-only output, unknown or
duplicate statuses, illegal
status/stage pairs, unknown schema versions, missing status-specific fields, and additional
terminal envelopes. A pure transition helper takes the validated envelope, launch kind
(`tests-only|full|continuation`), attempt number, session-resumability flag,
independent-verification result, and current task or cluster identity, then returns exactly one
next action: run RED, verify, obtain a concern ruling, resume, continue, replace, change the
blocking condition, escalate, or stop for user ruling. A `tests-only` launch returning `COMPLETE`
with `DONE`/`DONE_WITH_CONCERNS`, or a `full`/`continuation` launch returning `RED_READY`, is an
illegal stage for its launch and consumes the attempt like a malformed envelope. The helper's
output is the durable transition recorded in the ledger. It runs twice per launch: on the terminal
envelope (recorded by `implementation-attempt`) and, when that transition was `run-red`, `verify`,
or a resolved `concern-ruling`, on the host verification result (recorded by a `verification`
event). After `run-red`, valid RED yields `resume` when resumable, otherwise `continue` (a fresh
production launch sharing the attempt number); a result that is not valid RED is recorded as
`pass` or `regression`, consumes the attempt, and yields `replace`, `escalate`, or
`stop-user-ruling`. After `verify` or a resolved `concern-ruling`, a non-regression result yields
`complete`.

Every launched implementation delegate receives an explicit resolved model. Omission must not
inherit the orchestrator's potentially more expensive model. Phase 1 deliberately tightens
configuration compatibility for delegated implementation targets: each effective `claude` or
`opencode` implementation entry must resolve a model. Update the sample with both platforms and
document migration for existing configurations. A missing model stops preflight with a stable
diagnostic naming the exact selected configuration source, for example
`implementation.platforms.claude.high.model` or
`implementation.platforms.opencode.model`; review-only configuration remains valid. Implementation
entries stay objects (flat or level-keyed), never the candidate arrays used by review sections
(`resolve-flow.mjs` rejects arrays); the sample notes this, and a flat entry yields `exhausted`. Editing
configuration and re-invoking is the only remedy; the stop offers no ad-hoc `self` override.
A host applies only the target fields its native subagent launch supports (for example, a
model-alias-only launch with no effort field); `resolve-flow` reports the applicable
`{model, effort}` per platform, escalation distinctness compares applicable fields only, and an
inapplicable configured field is disclosed, never silently dropped.

Targets mapped to `self` launch no delegate and therefore do not require an implementation model
for execution. They record the orchestrator's actual model in attempt evidence when available;
configured `agy` or `copilot` implementation models remain compatibility metadata and do not
create an escalation tier while those platforms map to `self`.

An attempt is one launched implementation delegate for one task or fix cluster. Missing or
malformed terminal status, delegate failure or missing terminal outcome, `BLOCKED`, or a
`regression` independent-verification result consumes that attempt. `NEEDS_CONTEXT` pauses the
current attempt only
when the same delegate session can resume; launching a replacement delegate consumes the next
attempt. Resumability is true only when the launch returns a stable handle and the host exposes a
tested same-session continuation operation for that handle. Resumability defaults to false; a
host qualifies only when `skills/dispatch/references/providers.md` documents its continuation
operation. A delegate may receive at most one
context-only continuation per attempt. A second `NEEDS_CONTEXT`, or a materially identical request
after context was supplied, consumes the attempt and requires replacement or user ruling. Without
a resumable handle, the first `NEEDS_CONTEXT` consumes the attempt immediately.
`DONE_WITH_CONCERNS` requires an orchestrator ruling before independent verification. No task or
cluster may use more than three implementation attempts (the non-resumable tests-only RED launch
defined in Phase 0 is not an attempt), and failed delegated work never
transfers silently to the orchestrator. The counter resets only when an approved scope change
creates a new task or cluster.

When the resolved implementation target is `self`, the orchestrator performs the work and records
its own terminal status and attempt evidence under the same contract. There is no resumable
delegate session: one `NEEDS_CONTEXT` may pause for user clarification without consuming the
self-attempt; a second context request stops for a user ruling. Attempt 2 remains with the
orchestrator under the root-cause requirement. Model escalation is unavailable for `self`; if
Attempt 2 fails, record that limitation and stop for a user ruling. Self-execution is not a silent
takeover from a failed delegate. The retained trivial-work carve-out uses this same `self` contract
and records its status and attempt.

### Escalation ladder

1. **Attempt 1:** primary delegate implements test-first.
2. **Attempt 2:** when resumable, the same delegate receives the recorded failure evidence and the
   instruction to identify root cause before modifying code. Otherwise a same-platform,
   same-model replacement receives that evidence and consumes Attempt 2.
3. **Attempt 3:** the same native implementation platform uses the next higher configured
   implementation level that resolves to a distinct model or effort among the fields the target
   launch applies, carrying the failure history
   and root-cause analysis.
4. **Termination:** any failure after Attempt 3 stops the run and records a stable failure for user
   ruling, even if the error changed between attempts.

Implementation escalation uses the existing ordered levels
`low → medium → high → xhigh → max`. Starting above the requested level (not the nearest-lower key
`selectLevel` resolved it to), select the first defined level key whose resolved `{model, effort}`
differs from Attempt 2's. Escalation changes only the implementation target, never the settled
review level. If none exists (flat entries or a
`max` start), stop after Attempt 2 for the same stable-failure user ruling, recording that
escalation is unavailable; implementation never crosses to a reserve provider.
Routing uses effective configuration and does not hard-code model names. Flat implementation
entries intentionally resolve identically at every level and therefore provide no escalation tier;
the workflow must not synthesize one. This native-only rule supersedes the source comparison's Q3
proposal to fall back to a reserve provider because reserve candidates are review-only and do not
carry native write authority.

`NEEDS_CONTEXT` does not authorize the orchestrator to take over silently. `BLOCKED` does not
authorize an identical retry.

The resolved execution target, rather than configuration shape, controls escalation. A platform
that maps to `self`, including the current `agy` and `copilot` mappings, follows the two-attempt
`self` path even when its configuration contains multiple implementation levels; `resolve-flow`
returns `exhausted` with reason `self-target` for it.

## 6. Phase 2 — Durable execution ledger and rulings

### Objective

Persist execution position independently of walkthrough freshness so a compacted or fresh
orchestrator can reconstruct completed work before dispatching again.

### Ledger identity and location

`resolve-artifact-paths.mjs` adds an additive `ledgerPath` field:

```text
<os.tmpdir()>/dispatch-skills-<username>/<repo-hash>/<slug>-ledger.md
```

`<repo-hash>` is the first 12 lowercase hexadecimal characters of SHA-256 over the canonical
absolute result of `git rev-parse --show-toplevel`: `fs.realpathSync.native`, NFC, forward
slashes, and on win32 lowercased. The local root, rather than the remote URL,
keeps resolution offline and isolates worktrees.

The ledger is append-only, is not a review artifact, is not relocated at handoff, and does not
participate in plan or walkthrough freshness. Its dedicated per-user `dispatch-skills-<username>/`
namespace is intentional: unlike ephemeral runner logs and prompt spills, the ledger must remain
available for resume until the OS purges it.

The per-user ledger root uses mode `0o700`; ledger files use `0o600`. Modes apply on POSIX only;
on Windows, isolation relies on the per-user `%TEMP%`, and permission tests are platform-gated. Extract or reuse dispatch
telemetry's sanitized per-user naming convention for `<username>` so users sharing a system temp
directory cannot collide with or write one another's ledgers; the existing global runner-log path
is not the source of this contract.

`<slug>` is the canonical ordinary-plan slug or phased technical-design slug. A resumable
implementation requires an explicit or branch-derived slug. When initial artifact resolution
reports `slugSource: "conversation"` or no slug, the orchestrator chooses and persists an explicit
slug at that step, before authoring the governing artifact, so its plans, walkthroughs, and ledger
share one canonical identity. The resolver emits `ledgerPath` only for `explicit` or `branch`
slugs; with `conversation`, or outside a Git work tree, it emits `ledgerPath: null`, and resume
uses the best-effort missing-ledger path below. `resolve-artifact-paths.mjs` names no downstream
skill for `ledgerPath`; `dependency-direction.test.mjs` asserts this.

Phase 2 adds the additive ordinary resume form `/implement-dispatch <plan-path>`: the slug comes
from the plan's canonical filename (a `<plan-path>` without a canonical scratch filename is
rejected with a stable diagnostic), and resume proceeds only when the recomputed `governingHash`
matches the latest unterminated segment. Ordinary handoff and interruption reports print this
command and the ledger path, noting that OS temp (including Windows Storage Sense) may purge it.

`governingHash` for an ordinary run is the plan's dispatch-metadata `contentHash` (body after
frontmatter removal, shared normalization) at approval; resume recomputes it the same way, so
checkpoint metadata rewrites do not break resume.

The ledger is segmented by append-only `run-start` and `run-complete` events. `run-start` is
appended when the user approves the governing artifact, immediately followed by the `approval`
event; pre-approval rulings and reviews already recorded in the walkthrough and resolution logs
are appended after it. `run-start` records a
run ID, canonical governing-artifact hash, root slug, and a baseline tuple:

- `commit`: the immutable `HEAD`, or the empty-tree object ID for a repository without commits;
- `repositoryState`: a canonical fingerprint of the materialized path state of `dirtyPaths` plus
  index state at run start (clean paths are implied by `commit` and contribute no record to the
  materialized digest); and
- `dirtyPaths`: the sorted paths whose index or materialized state differs from `commit`.

The run baseline path universe (used to derive `dirtyPaths` from Git status) is every tracked path
plus every untracked, non-ignored path reported by Git at `run-start`; full content records are
hashed only for `dirtyPaths` and task-owned paths; `.git/`, `.scratch/`, ignored paths, and uninitialized submodule
contents are excluded. Governing artifacts are identified by their own hashes, not the fingerprint,
and no task path set may include `.scratch/`. A task or cluster uses exactly its declared repository-relative path set. When the approved path
set is the §4 whole-repository fallback, task `preState`/`resultState` hash only paths that differ
from `commit` at that event plus paths the task mutated; clean paths are implied by `commit`, as
for the baseline. An owned path
added after `run-start` enters that task's universe before its `task-start` fingerprint. Sparse
checkout entries outside the materialized cone are represented from the index and marked
`worktreeAbsent`; a submodule is one gitlink record containing mode `160000`, index object ID, and
materialized submodule `HEAD` when available. Symlinks hash their link-target bytes, not target
contents.

The materialized path-state fingerprint covers only its hashed path set (`dirtyPaths` for the
baseline; the declared task paths for task states) and is SHA-256 over length-prefixed records sorted by raw Git
repository-relative pathname bytes obtained from NUL-delimited plumbing output. Event and
diagnostic paths must decode as UTF-8; an undecodable path stops preflight with a stable
unsupported-path diagnostic rather than being lossy-normalized. Each record encodes pathname
length and bytes, existence,
Git-compatible mode (`100644`, `100755`, `120000`, `160000`, or `absent`), content length and raw
bytes or the explicit absent marker, and the sparse/submodule fields above. Deletions use an absent
record; renames are one absent old path plus one present new path. Line endings and binary content
remain raw bytes.

The index fingerprint is a separate SHA-256 over records sorted by pathname bytes then stage
number. Each record contains pathname length and bytes, stage `0..3`, mode, and object ID from
`git ls-files --stage`; an unmerged path therefore retains every conflict stage. Intent-to-add is
recorded with its zero object ID and index flags. `repositoryState` is SHA-256 over a framed version
tag, the materialized digest, and the index digest. Before each task or cluster dispatch, record the
materialized fingerprint for its declared path set as `preState`. Task `preState`/`resultState`
are materialized-path digests only; the index digest belongs to `run-start.baseline.repositoryState`
alone, so staging or committing never changes task completion identity. This pre-state attributes
pre-existing dirty content to the baseline rather than to the task.

Ordinary resume considers only the latest unterminated segment whose plan hash matches; a
completed or mismatched segment is never resumed implicitly. Phase 5 extends this rule for
multi-invocation design runs.

### Event grammar

Each event occupies one newline-terminated markdown list item whose value is one canonical JSON
object:

```markdown
- event: {"v":1,"seq":1,"type":"run-start","runId":"...","at":"...","data":{...}}
```

Phase 2 ships version `1` (the `v1` rows below); Phase 5 adds version `2` (the `v2` rows and
column notes). A v2 reader folds v1 events unchanged, and a v1 reader treats v2 events as unknown.
Every envelope requires `v` (integer `1` or, from Phase 5, `2`), `seq` (positive integer), `type` (listed enum), `runId`
(UUID string), `at` (UTC RFC 3339 timestamp with milliseconds), and `data` (object). Canonical JSON
normalizes non-path strings to NFC (path strings keep Git's raw bytes decoded as UTF-8), permits only integers for numbers, sorts object keys by Unicode code
point, preserves array order, uses no insignificant whitespace, and UTF-8 encodes the result.
The event types and exact required `data` properties are:

| Ver | Type | Required data |
|---|---|---|
| v1 | `run-start` | `governingPath:string`, `governingHash:sha256`, `rootSlug:string`, `action:"ordinary"`, `baseline:{commit,repositoryState,dirtyPaths:string[]}`; v2 widens `action` to `"ordinary"|"design"|"increment"|"integration"`; for phased actions `governingPath`/`governingHash` are the design path and approved governed revision, `design:{path,revision}` is required, and `increment:{id,planPath,walkthroughPath,planHash}` is required when `action` is `"increment"` |
| v1 | `run-complete` | `result:"complete"|"stable-failure"|"aborted"`, `evidenceRefs:string[]` |
| v1 | `task-start` | `taskId:string`, `attemptBudget:integer`, `paths:string[]`, `preState:sha256`, optional `parentTaskId:string` |
| v1 | `implementation-attempt` | `taskId:string`, `attempt:integer`, `launch:"tests-only"|"full"|"continuation"`, `target:{platform,model?,effort?,sessionHandle?}`, `terminalEnvelope:object|null` (`null` when missing or malformed), `evidence:string[]`, `transition:transition-enum` |
| v1 | `verification` | `taskId:string`, `attempt:integer`, `result:"red"|"pass"|"accepted-baseline-equivalent"|"regression"`, `commandRefs:string[]`, `transition:transition-enum`; `failureIdentity:object` required when `result` is `red` |
| v1 | `task-complete` | `taskId:string`, `paths:string[]`, `head:object-id`, `preState:sha256`, `resultState:sha256`, `diffHash:sha256` |
| v1 | `ruling` | `key:string`, `decision:string`, `reason:string`, `costIfWrong:string` (one-line orchestrator estimate; `"n/a"` for user-owned rulings), `state:"open"|"resolved"|"superseded"` |
| v1 | `review` | `kind:"plan"|"code"`, `round:integer`, `counts:{accepted,rejected,resolvedDispute,disputed,pendingConfirmation,unknown}` (copied from `scanResolutionLog()` round counts), `checkpointRef:string`; v2 adds `"design"|"integration"` to `kind` |
| v1 | `approval` | `governingHash:sha256`, `decision:"approved"|"rejected"`, `actor:"user"`; for v2 design approvals `governingHash` is the governed-content revision (§9) |
| v2 | `increment-state` | `incrementId:string`, `prior:increment-state`, `next:increment-state`, `cause:string`, `affectedDependents:string[]` |
| v2 | `amendment` | `amendmentId:string`, `state:amendment-state`, `baseRevision:sha256`, `candidateHash:sha256`, `affectedIncrements:string[]`; `targetPath:string` and `replacementPath:string` required when `prepared`; optional `reconciliationState:string` |
| v2 | `adjacent-fix` | `findingIds:string[]`, `clusterId:string`, `attempts:integer[]`, `result:"complete"|"failed"|"aborted"` |
| v2 | `integration` | `scopeId:string`, `verificationRefs:string[]`, `reviewRefs:string[]`, `result:"pass"|"accepted-baseline-equivalent"|"regression"` |

`transition-enum` is
`run-red|verify|concern-ruling|resume|continue|replace|change-blocking-condition|escalate|stop-user-ruling|complete`
(`complete` only on a non-regression `verification`). `seq` is ledger-global and strictly
increasing across segments. `task-complete.head` is `git rev-parse HEAD` at completion (the
empty-tree ID without commits, obtained from `git hash-object -t tree --stdin` with empty input so
SHA-1 and SHA-256 repositories both work); it moves only if the user committed.
`increment-state` is
`pending|ready|active|complete|blocked|invalidated|reopened`.
`amendment-state` is
`proposed|reviewed|prepared|activated|rejected|aborted`.
All paths are normalized repository-relative slash-separated strings; all SHA-256 values use the
existing dispatch-metadata form `sha256:<64 lowercase hex>`, so ledger and metadata hashes compare
directly. Git object IDs (`commit`, `head`) stay raw 40- or 64-character hex, matching
`baseSha`/`headSha`. Optional properties are the only additional properties allowed
by the versioned schema.

Unknown properties, versions, enum values, or event types; duplicate or decreasing sequence
numbers; missing required fields; and malformed interior lines block resume as
`needs-reconciliation`. Reconciliation is a derived fold state of an unterminated segment, never a
`run-complete` result; a resolved `ruling` with key `reconciliation` clears it. A malformed or non-newline-terminated final line is treated as an
interrupted append: copy the torn bytes into the diagnostic, truncate the file on disk to the end
of the last valid newline-terminated line, and require reconciliation before another dispatch, so
the next append never follows invalid bytes. Each append writes one complete serialized line through one descriptor,
calls `fsync` on that descriptor, and only then reports the transition successful.

Rulings are keyed; a later `ruling` with the same `key` supersedes the earlier one (highest `seq`
wins). A red-baseline decision is a ledger ruling with key `baseline-red`, mirrored in the
walkthrough; `plan-lint` is a preparation stop, not a ruling.

Task events retain a deterministic diff hash for audit, computed at completion from canonical
before/after path-state records. Resume proves unchanged completion with the result-state
fingerprint, which survives a later commit because it ignores Git storage layer. When a later
valid event owns an overlapping path, its result-state is authoritative for that path and the
earlier task is not redispatched solely because its historical result-state no longer matches.
Non-review decisions use `ruling`; review decisions remain authoritative in existing plan and
walkthrough resolution logs and are referenced by `review`.

Legal ordering is: `run-start` first; zero or more rulings/reviews/approvals; each `task-start`
precedes attempts for that task; attempt numbers start at `1` (a split descendant with
`parentTaskId` continues from its parent's latest attempt number plus one) and increase by at most
one per event (a `tests-only` launch and its `continuation` share a number); a `verification`
follows the attempt whose transition was `run-red`, and a `continuation` launch requires a
preceding valid `red` verification for that task and attempt; a non-RED-gate `verification`
follows the attempt whose transition was `verify` or a resolved `concern-ruling`, at most one per
(task, attempt); `task-complete` follows a `verification` whose transition is
`complete`; `adjacent-fix` follows the task events of its cluster; an `amendment` follows the
active increment's latest task event and precedes the `increment-state` transitions it causes; `integration`
occurs only in an `integration` action, after its verification/review evidence; increment and
amendment events reference an existing design binding; `run-complete` is last. A completed task cannot restart unless an `increment-state` event reopens
its owning increment. Amendment states follow
`proposed → reviewed → prepared → activated`, with `rejected` or `aborted` terminal from any
pre-activation state. Increment states may move
`pending → ready → active → complete`, any unfinished state to `blocked` or `invalidated`,
`complete → reopened`, `reopened → active`, `blocked → ready`, and `invalidated → pending` after
an activated amendment; all other transitions are illegal. Ordering rules that name v2 events apply
only once those events exist (Phase 5); Phase 2 implements and tests the v1 rules only.

The fold processes valid events by `seq` within each segment. It rejects illegal transitions,
reconstructs the latest task/cluster and increment states, carries attempt lineage and remaining
budget, keeps unresolved rulings and reconciliation states live, and treats `run-complete` as
terminal for that segment. Phase 5 adds cross-segment folding for a matching design identity.

### Resume behavior

Before any dispatch after compaction or in a fresh session:

1. Resolve the deterministic ledger path.
2. Read all valid ledger events.
3. Compare each currently authoritative result-state fingerprint with the materialized state of
   its paths, preserving equivalence when unchanged content was committed.
4. Reconstruct completed tasks, active task, retry count, and unresolved rulings.
5. Dispatch only work not proven complete by both ledger and working tree evidence.

Hash drift enters `needs-reconciliation`; it does not automatically redispatch a task when a later
ledger event owns any of the same paths. Reconciliation must attribute the live diff before work
continues.

If the OS purged the ledger, reconstruct best-effort state from the working tree and retained
governing artifacts. The absence of a ledger is recoverable and must not produce a success-shaped
assumption.

- Different worktree roots resolve to different paths.

## 7. Phase 3 — Deterministic plan lint

### Objective

Stop structurally unexecutable plans before cross-provider review while preserving reviewers'
responsibility for semantic judgment.

### Validation rules

Blocking defects return:

```json
{
  "schemaVersion": 1,
  "kind": "plan",
  "action": "<preparation-action>",
  "status": "decision-required",
  "decision": "plan-lint",
  "artifact": { "canonicalPath": "<path>", "tier": "<tier>", "slug": "<slug>" },
  "freshness": { "status": "<status>", "changedSections": [] },
  "defects": [{ "rule": "<rule-id>", "locus": "<section-or-line>", "message": "<diagnostic>" }],
  "cleanupPaths": []
}
```

`plan-lint` has no `choices` and is never replayed as a request `decision`. In orchestrated mode,
the orchestrator fixes its in-run plan and prepares again. Standalone mode stops with the
diagnostics so the plan owner can edit and rerun. `defects` is the only additive field on the
existing `decision-required` manifest envelope, and `plan-lint` omits `choices`. Amend `dispatch-plan-review`'s generic
`decision-required` step to branch on `decision`: only decisions with non-empty `choices` are
asked and replayed; `plan-lint` is reported and stops without an ask.

Blocking rules:

- The plan lacks a unique `## Proposed Changes` containing at least one `[NEW]`/`[MODIFY]`/
  `[DELETE]` H4 change heading.
- The same path appears under more than one change heading (duplicate or conflicting `[NEW]`,
  `[MODIFY]`, `[DELETE]` actions).
- The plan lacks a unique `## Verification Plan`, its `### Automated Tests` is missing or
  duplicated, an `### Automated Tests` appears outside `## Verification Plan`, or that H3 has neither a fenced/backticked
  command nor an explicit `- None: <reason>` item. A `- None: <reason>` item is not a blocker: it is
  a warning and becomes a Phase 0 `unavailable` record.
- A present `## Success Criteria` item has neither a syntactic `Changes:` path reference nor a
  `Verify:` command, or names a `Changes:` path absent from every change heading.

Add `## Success Criteria` to the canonical plan template as an H2 immediately before
`## Proposed Changes`, and rewrite the template's `### Automated Tests` placeholder as one
inline-code command per bullet. Each item has a stable criterion ID and
at least one machine-readable mapping:

```markdown
- [SC1] <criterion>
  - Changes: <relative-path>[, <relative-path>...]
  - Verify: `<command>`
```

At least one of `Changes:` or `Verify:` is required per criterion. The linter checks references,
not whether the named change or command is semantically sufficient.

Non-blocking warnings are included in reviewer prompt context:

- structural: no `## Success Criteria` section in a legacy plan; native-tier plan defects (below);
  `- None: <reason>` automated tests;
- placeholders: `TODO`, `TBD`, `implement later`, `fill in`.

The linter checks structure and command presence only. It never executes verification or attempts
to determine whether a command is correct for the host.

The linter parses Markdown headings and list structure rather than searching raw text:

- Section names are case-sensitive literal headings. The linted headings are `## Proposed
  Changes`, `## Success Criteria` (optional), `## Verification Plan`, and its `### Automated
  Tests`; each present one must occur exactly once under the expected parent, and duplicates are
  blocking defects. Other template headings are not linted.
- Fenced code, HTML comments, block quotes, and inline code are excluded from headings, action
  markers, criterion labels, paths, and placeholder warnings. The sole exception is command
  extraction described below.
- `[NEW]`, `[MODIFY]`, and `[DELETE]` are recognized only in H4 change headings beneath
  `## Proposed Changes`. Their path, backticked or plain as in the template, is slash-normalized, must be repository-relative,
  and compares case-sensitively after `.` segment removal; `..`, absolute paths, and backslashes
  are invalid.
- Success criteria are top-level list items directly beneath `## Success Criteria` whose text
  starts with `[SC<positive-integer>]`. IDs are unique; an unlabelled top-level item there is a
  blocking defect. Their indented child bullets recognize
  exact `Changes:` and `Verify:` labels only. `Changes:` contains comma-separated backticked or
  plain normalized paths; `Verify:` contains exactly one inline-code command.
- `### Automated Tests` belongs to the unique `## Verification Plan`. A command is either a
  non-empty line not starting with `#` in a fenced block under that H3, or the sole inline-code
  span of a direct list item (items with several spans are a warning, not commands).
  Prose backticks elsewhere do not satisfy the rule.
- Placeholder warnings inspect prose nodes outside fences/comments and match ASCII
  case-insensitively on word boundaries.

`Changes:` bullets under `[NEW]`/`[MODIFY]`/`[DELETE]` change blocks are outside
`## Success Criteria` and never satisfy or trigger the criterion rule.

Apply blocking rules to plans owned by this workflow: `request.artifactOwned === true`, a plan
authored in-run, or an explicitly supplied plan. A platform-native plan is not guaranteed to use
this repository's headings; report the same defects as reviewer-visible warnings rather than
blocking `plan-lint` failures. A non-owned `scratch-existing` plan first receives the existing
`legacy-plan-coverage` decision (lint defects shown as warnings), because `overwrite` and
`fresh-slug` discard it; blocking lint applies only after an `as-is` ruling.

### Integration surfaces

- `skills/dispatch-plan-review/scripts/prepare-review.mjs`: invoke lint after reading the canonical
  artifact and before creating dispatch files.
- `skills/dispatch-plan-review/references/plan-template.md`: add the structured
  `## Success Criteria` section.
- A pure lint helper beside `prepare-review.mjs` if needed for focused unit tests.
- `tests/skills/dispatch-plan-review/prepare-review.test.mjs`: one case per blocking defect,
  warnings in prompt context, clean plan behavior, duplicate/heading/path/indentation/command
  boundaries, fenced/comment exclusions, and a `[MODIFY]`-block `Changes:` false-positive case.
- `skills/dispatch-plan-review/SKILL.md`: document blocking and warning outcomes.
- `skills/implement-dispatch/SKILL.md` § 2: on `decision: "plan-lint"` for an in-run plan, edit
  the plan to clear every `defects[]` entry and re-prepare; no ask or replay, and it consumes
  neither review rounds nor budget.

### Completion gate

- Every blocking rule returns `decision-required` before prompt, batch, or dispatch files are
  created.
- Lint blockers return `decision: "plan-lint"` with structured defects, no choices, and cannot be
  replayed as a request decision.
- Warning-only plans remain `ready` and every warning is visible to all review targets.
- Canonical fixtures are upgraded to the new template and remain `ready`; legacy fixtures without
  `## Success Criteria` remain `ready` with a warning. Legacy plans missing required verification
  structure return `decision-required / plan-lint` without creating review files when they are
  scratch-tier or explicit workflow-owned artifacts; native-tier plans remain reviewable with
  warnings.
- A non-owned `scratch-existing` plan with lint defects returns `legacy-plan-coverage` first (defects
  as warnings); `as-is` then returns blocking `plan-lint`, while `overwrite` re-authors.
- Tests prove that the linter detects syntax, not host semantics.
- `implement-dispatch` fixes an in-run plan on `plan-lint` and re-prepares without a user ask.

## 8. Phase 4 — Keyed opt-ins and clustered follow-up fixes

### Objective

Make deferred decisions easy to toggle and reduce review cycles by processing independent accepted
fixes as clusters instead of one finding at a time.

### User-facing opt-ins

At ordinary-plan settlement and at handoff (Phase 5B extends this to increment settlement), render
two distinct sections when decision-changing items exist. Sequence at settlement: render, apply the
response, materialize the resulting scope, rerun lint/flow/required review, then present approval
including the materialized scope.

```markdown
### Recommended Follow-ups (Default: Included)
- [R1] [x] Fix type cast in foo.ts — addresses the reviewed edge case.

### Out-of-Scope / Adjacent Items (Default: Excluded)
- [O1] [ ] Add telemetry metrics — deferred to a separate change.
```

- Only settled, accepted-but-unapplied `SHOULD` and `CONSIDER` findings are recommendation
  candidates and default to included unless the orchestrator records a one-line reason to exclude
  them; an excluded candidate renders unchecked with that reason and stays toggleable. Applied, rejected, superseded, disputed, or pending findings are ineligible.
- `adjacent` and other out-of-scope items default to excluded.
- Keys are stable within the approval or handoff interaction and support replies such as
  `exclude R2, include O1`.
- When no items exist, state `none` without asking a question.
- Review finding IDs remain authoritative in resolution logs; `[R#]` and `[O#]` are interaction
  aliases, not replacements.
- `[R#]` aliases accepted-but-unapplied in-scope recommendations. `[O#]` aliases verified adjacent
  or explicitly deferred out-of-scope findings. Alias generation deduplicates by authoritative
  finding ID and never revives a settled rejection.
- Before approval, materialize default-included recommendations into proposed changes, success
  criteria, and verification mappings, then rerun lint, flow resolution, and any required plan
  review. Any materialization, default or toggled, re-checkpoints plan freshness metadata before
  approval is accepted; a toggle that changes executable scope keeps the same logical approval gate
  open but repeats settlement.
- At settlement and at handoff, a non-empty opt-in set requires an explicit response; accepting
  the defaults is a response, not silence. Including an `O#` item triggers the one-way scope rule;
  at handoff it re-enters flow resolution and runs as an adjacent-fix cluster with a fresh budget
  (an approved scope change).

### Finding application record

The resolution log remains authoritative for adjudication and gains one canonical JSON
continuation immediately after each accepted finding that can survive settlement unapplied:

```markdown
  - application: {"v":1,"findingId":"R1-F001","state":"unapplied","scope":"in-scope","affectedPaths":["src/foo.ts"],"dependsOn":[],"verification":["npm test -- foo"],"reason":"default recommendation"}
```

The record requires `v:1`, `findingId`, `state`
(`unapplied|materialized|applied|superseded`), `scope` (`in-scope|adjacent`), sorted unique
repository-relative `affectedPaths` (non-empty), sorted unique finding IDs in `dependsOn`,
`verification` (a non-empty deduplicated command list when the finding touches executable
behavior, otherwise `[]` with `reason` stating why), and `reason`. The host creates or
updates it only after verifying the finding and enriching it from the settled plan, changed scope,
and repository commands; reviewer output alone is not authoritative for these fields. A plan
finding that changes only plan prose and no repository path is applied to the plan during
settlement and carries no application record.
`resolution-log.mjs` parses and validates these continuations and exposes them with the finding
rather than discarding locus/resolution data needed by later clustering.

During plan or code settlement, accepted `MUST` findings remain immediate required fixes. Accepted
`SHOULD` and `CONSIDER` findings may remain `unapplied` only with a complete application record;
they enter the keyed recommendation interaction and default to included. Materializing a selection
updates it to `materialized`; successful implementation and verification update it to `applied`.
An accepted finding that is intentionally deferred records the reason and remains `unapplied`.
When a later review round, rebuttal, or user ruling supersedes an accepted finding, its record
moves to `superseded`.
Rejected, disputed, pending, or superseded findings cannot have a live application record.
This replaces the current unconditional application of safe accepted `SHOULD` findings in the
orchestrated plan-settlement path. Standalone `dispatch-code-review` keeps auto-applying safe
accepted fixes (no interface change) but applies them as independence clusters.

### Cluster behavior

1. Group findings only when their affected path sets are pairwise disjoint and they have no
   declared ordering, interface, or verification dependency. Keep same-file findings separate;
   when dependency is uncertain, keep the findings separate.
2. Dispatch one implementation task per cluster.
3. Run the deduplicated union of every member finding's required verification commands, then one
   scoped review loop per cluster; every command must pass.
4. If a cluster fails, retain the current working tree, preserve completed clusters, and split only
   the failed cluster into smaller independently provable groups. Attribute and reverify partial
   outcomes before redispatching remaining work.
5. Apply the Phase 1 escalation ladder within each orchestrated `implement-dispatch` cluster.
   Standalone `dispatch-code-review` clusters keep its existing two-identical-failures guard per
   cluster instead.

A split is recovery, not approved scope growth. Every descendant cluster inherits the parent
cluster's attempt lineage and shares its remaining budget; splitting never resets or multiplies
attempts. Work proven complete within the failed parent is recorded without another dispatch.
When no attempt remains for an unfinished descendant, stop for the Phase 1 user ruling. Only a
separately approved scope change may create a new cluster with a fresh budget.

A cluster ID is deterministic: `C-` plus the first 12 hex characters of SHA-256 over
`<runId>|<parentTaskId or ''>|<sorted member finding IDs joined by ','>`, so it survives compaction
without colliding with an earlier cluster of the same members.
Each cluster is an ordinary v1 ledger task: one `task-start` whose `taskId` is the cluster ID,
`paths` is the members' union path set, and `attemptBudget` is the remaining budget; a split
descendant sets `parentTaskId` to the failed parent; `implementation-attempt`, `verification`,
and `task-complete` record the rest. Phase 4 adds no event type.

- `skills/implement-dispatch/SKILL.md`: approval, handoff rendering, response application,
  cluster lifecycle, and cluster ledger append points.
- `skills/dispatch-code-review/SKILL.md`: standalone accepted-fix clustering and unbundling; safe
  accepted fixes remain auto-applied.
- `skills/dispatch/references/alignment.md`: interaction aliases and their relationship to stable
  finding IDs.
- `skills/dispatch/scripts/resolution-log.mjs` and its tests: parse, validate, and expose finding
  application records.
- Every strict `scanResolutionLog` consumer (`check-consensus.mjs`, `review-preparation.mjs`, both
  `prepare-review.mjs` scripts), `alignment.md` § Resolution log, and a strict-mode round-trip
  test: accept the `application:` continuation without breaking semantic-body hashing.
- Plan/code review report schemas remain claim-only; the host enriches verified findings after
  adjudication so providers do not invent path, dependency, or command metadata.
- Existing consensus, rebuttal, and preparation scripts remain the source of truth for review
  settlement and consume the enriched resolution-log records.

### Completion gate

- Recommended and out-of-scope items have distinct defaults and stable aliases.
- No prompt is emitted when both sets are empty.
- Independent fixes produce one dispatch, verification, and scoped review per cluster.
- A failed cluster can be split without repeating successful cluster work.
- Cluster splitting cannot produce a fourth implementation attempt across a parent and its
  descendants.
- Tests cover disjoint paths with a shared dependency, multiple verification commands, and one
  failed item inside a multi-item cluster.
- Resolution logs retain original finding IDs, application metadata, and final disposition.
- Cluster lineage survives resume through v1 `task-start.parentTaskId` without new event types.

## 9. Phase 5 — Technical design and incremental execution

### Objective

Support genuinely large changes through one approved technical design and a sequence of bounded,
independently reviewable implementation increments while preserving the existing single-plan path
for ordinary work.

### Delivery gates

Phase 5 is implemented through two independently completable gates:

- **Phase 5A — Design foundation:** terminology, activation/classification, kind-aware artifact
  resolution, `dispatch-design-review`, technical-design review/freshness, approval persistence,
  and the post-approval durable stop. Phase 5A must not advertise increment execution as available.
- **Phase 5B — Increment execution:** implementation-plan binding, ledger folding, one-increment
  execution, amendments, aggregate final integration, and final artifact relocation. Phase 5B
  begins only after every Phase 5A completion criterion passes.

Phase 5A ships the v2 `design` `run-start`/`run-complete` and design `approval` events; Phase 5B
ships `increment-state`, `amendment`, `adjacent-fix`, and `integration`.

Both gates are part of v0.4; this split controls implementation and review risk rather than
deferring the approved capability to another version.

### Canonical terminology

Use these terms normatively throughout the workflow:

| Term | Meaning |
|---|---|
| **Technical design** | The reviewed high-level solution: intent, acceptance, architecture, invariants, trade-offs, risks, and implementation-increment dependency graph. |
| **Implementation plan** | The concrete repository-level execution plan for one approved implementation increment. |
| **Implementation increment** | One coherent outcome or enabling seam that leaves the repository in a valid, verified, independently reviewable state. |
| **Workstream** | A parallel-safe lane organized by subsystem, capability, or ownership. |
| **Checkpoint** | Keeps its existing meaning: the review-metadata checkpoint written after review settlement. Use `milestone` only for a significant project-level achievement, not for a body of implementation work. |
| **Batch** | A temporary dispatch, verification, or review grouping chosen for execution efficiency. |
| **Task** | The smallest actionable unit inside an implementation plan. |

This separation follows common design-document and incremental-delivery practice: the technical
design governs the solution and its boundaries, while implementation plans translate one approved
increment into concrete edits and verification. Do not use `spec`, `root plan`, `roadmap`,
`milestone sub-plan`, `phase`, or `batch` as interchangeable aliases for these artifacts or units.
This document's delivery "Phases" are release sequencing only and must not appear in shipped
skill prose. Shipped "phase" keeps its existing meaning (plan-review, implementation, and code-review stages); the implementation-envelope field is `stage`, not `checkpoint`.

### Activation, promotion, and downgrade

Activate phased execution when the work requires more than one independently valid implementation
increment because of demonstrated evidence such as:

1. **Dependency gates:** later work cannot be implemented, compiled, migrated, or verified safely
   until an earlier foundation exists.
2. **Distinct risk or verification boundaries:** parts of the change have materially different
   blast radius, rollback treatment, verify commands, or review concerns.
3. **Migration or compatibility staging:** the repository must pass through multiple green states,
   such as expand, migrate, and contract or preparatory refactor, behavior switch, and cleanup.
4. **Context or review limits:** one plan, expected diff, or review packet would not remain coherent
   and reviewable as a single unit.
5. **Explicit user direction:** the user requests technical-design-driven incremental execution.

The orchestrator cites the qualifying evidence and the candidate increments when it classifies the
request. It enters technical-design authoring without a separate mode-approval prompt, but the user
may challenge the classification during clarification. File count, line count, task count, a
mechanical API migration, or an ordinary cross-cutting edit is not sufficient by itself.

An ordinary run that grows beyond one coherent increment promotes to this mode whenever the
qualifying evidence appears. Before code writes, its settled decisions become technical-design
inputs directly. After code writes, stop further writes, fingerprint and reconcile the live diff,
then classify it as a candidate initial increment or explicitly abandoned work before authoring
the design. No additional implementation proceeds until design review and approval settle.
Downgrade to the ordinary path is permitted only before technical-design approval and only when
the qualifying evidence has demonstrably disappeared. An approved phased run never silently
downgrades.

### Technical-design contract

`implement-dispatch` authors the governing design at:

```text
.scratch/plan/<yyyy-mm-dd>-<slug>-design.md
```

Phased artifacts always use the scratch tier. Native plans and walkthroughs are never eligible as
technical designs, increment artifacts, or final-integration artifacts. Once assigned, the
design's date and slug and each increment's ID, slug, and artifact paths are immutable. Every
phased artifact path uses the design's canonical date, never its own authoring date.

Artifact resolution is kind-aware. Ordinary discovery must not classify a metadata-valid design,
increment plan/walkthrough, or integration walkthrough as an ordinary plan, even when its filename
matches the ordinary `<date>-<slug>.md` shape. Explicit ordinary slugs that would create a
canonical phased suffix collision are rejected with a stable diagnostic; the reserved forms are
slugs ending in `-design`, `-integration`, or `-integration-walkthrough`, and slugs matching
`-i\d{2}-.+-(?:plan|walkthrough)$`. Legacy files without
kind metadata retain current ordinary discovery behavior.

`dispatch-design-review` can also author or review the same artifact as a standalone workflow.
Technical-design authoring asks the user about decision-changing ambiguities rather than silently
defaulting intent. The design contains:

- context, problem statement, and clarified user intent;
- goals, non-goals, requirements, and acceptance criteria;
- constraints, architecture, domain invariants, and shared interface or ownership boundaries;
- alternatives considered, trade-offs, risks, and unresolved questions;
- data, migration, compatibility, rollout, and rollback treatment where applicable;
- an implementation-increment dependency graph and a governed, author-assigned total priority order
  among increments, changed only by amendment;
- for each increment, a stable `I01`, `I02`, ... ID, outcome, prerequisites, scope, intentional
  non-scope, observable behavior, affected contracts, validation, rollback boundary, and
  parallel-safety declaration;
- final cross-increment integration and verification requirements;
- durable decisions and technical-design review findings and resolutions; and
- a machine-managed `Execution Status` section showing completed, current, ready, blocked, and
  invalidated increments plus one explicit `Next Action`.

`Next Action` is derived from the ledger and is exactly one of: implement a named ready increment;
resolve a named reconciliation, amendment, or user ruling; run final integration; or complete.

The technical design must remain high-level. It must not contain exhaustive file-by-file edits,
symbol-level instructions, or task checklists that belong in an implementation plan.

### Design review, approval, and freshness

Add a thin `dispatch-design-review` skill with its own template and design-specific review overlay,
backed by the same preparation, dispatch, claim-verification, consensus, checkpoint, and
resolution-log machinery as `dispatch-plan-review`.

Both review modes share checks for intent fidelity, correctness and invariants, compatibility,
testability, simplicity, scope control, and repository standards. The design overlay additionally
checks architecture, system boundaries, alternatives, cross-cutting interfaces and data flows,
security and operational concerns, migration and rollback, risk concentration, increment
cohesion, dependency-graph correctness, parallel safety, and final integration coverage. It
verifies repository feasibility without demanding task-level detail. The implementation-plan
overlay instead checks one increment's concrete files, symbols, sequencing, error behavior,
prerequisite evidence, exact verification, and bounded blast radius.

Design review reuses the selected level's existing `plan-review` targets, rounds, consensus, and
enablement. When that policy disables review, approval explicitly discloses that no external
design review occurred. Do not add a `design-review` configuration block in v0.4.

After enabled design review settles, `implement-dispatch` presents the technical design once for
user approval. That approval replaces routine per-increment approval gates while every increment
remains inside the approved design. Persist approval as a governed-content revision and hash in
the ledger and artifact metadata. Compute the governed-content hash with the shared NFC/LF
normalization after removing dispatch frontmatter and excluding exactly `## Execution Status` and
`## Review Findings & Resolutions`; every other section, including the decision history, is
governed. The revision identifier is that SHA-256 digest.

Extend dispatch metadata with `kind: "design"`, plan-style `sectionHashes`,
`approvedContentHash`, and `approvedAt`. Review checkpoints merge and preserve valid approval
fields rather than replacing them; a newly reviewed but not yet approved governed hash clears the
approval fields. Before resume or dispatch, require the canonical recomputed governed hash to
equal both the metadata and ledger approval record. Every implementation plan binds to that
approved design revision.

Technical-design review consensus is not user approval. A standalone `dispatch-design-review` run
can settle review state, but only `implement-dispatch` records approval. After approval,
`implement-dispatch` records the first ready increment and ends the invocation before implementation
begins. This is a durable review and optional compaction boundary.

### Implementation-increment loop

Each increment uses a deterministic implementation-plan path:

```text
.scratch/plan/<yyyy-mm-dd>-<design-slug>-iNN-<increment-slug>-plan.md
```

Its paired walkthrough path is:

```text
.scratch/plan/<yyyy-mm-dd>-<design-slug>-iNN-<increment-slug>-walkthrough.md
```

Plan- and code-review preparation receive the explicit plan/walkthrough paths and the design slug;
they must not derive the ledger identity from either filename or invoke native-tier discovery.

Extend the existing plan template rather than replacing it. Add the parent technical-design path,
approved revision, increment ID and inherited contract, prerequisite evidence, and explicit
mapping from proposed changes and tests to the increment's acceptance criteria. Retain concrete
file and symbol changes, rollback and blast radius, verification, local decisions, open questions,
review findings and resolutions, and out-of-scope items.

Implementation-plan authoring asks the user when repository investigation uncovers a new
decision-changing ambiguity. Classify each answer as:

- **Local refinement:** it stays within the approved increment and is recorded in the
  implementation plan's decision history.
- **Design-changing:** it alters intent, acceptance, architecture, shared contracts, increment
  boundaries, or dependency edges and therefore enters the design-amendment path.

The implementation plan uses the configured `plan-review` policy. Once enabled review reaches
consensus, it proceeds without another routine approval prompt because the technical design is the
phased run's approval gate. Every implementer and reviewer receives bounded technical-design
context and the approved revision.

After plan settlement and keyed recommendation materialization, create the increment walkthrough
and run every selected baseline command before the first implementation dispatch, regardless of
whether code review is enabled. Record known-red or unavailable-command rulings under the Phase 0
contract.

v0.4 records parallel-safe increments but executes exactly one increment per invocation in the
current working tree. Among multiple ready increments, select the approved design's
highest-priority ready increment. Ask the user only when a material trade-off remains unsettled.
An increment is appropriately sized when it:

- delivers one coherent outcome or enabling seam;
- leaves the repository in a valid, verified state;
- fits one implementation-plan, implementation, and code-review context;
- has a comprehensible rollback and review boundary; and
- does not combine concerns with materially different risks or verification.

An increment need not be independently user-visible or deployable. Foundation, migration, and
cleanup increments are valid when their enabling outcome and invariants are explicit.

After implementation, verification, code review, and checkpoint settlement, update the ledger and
the design's execution-status mirror, including the next ready unfinished increment. End the
invocation and report:

- the completed increment and bounded diff;
- verification and review state;
- unresolved or deferred items;
- whether the completed work is committed;
- the exact `Next Action` and exact `/implement-dispatch <design-path>` resume command; and
- that this is a safe optional compaction point.

Commits and compaction remain user-owned and optional. Strongly recommend inspecting and, when
appropriate, committing the coherent increment. Resume must not depend on conversation context or
a commit: verify ledger events, design revision, artifact checkpoints, Git state, and deterministic
diff fingerprints before dispatching more work. If context pressure is known, elevate the
compaction recommendation.

The existing immediate adjacent-fix loop is the sole exception to one increment per invocation.
After the approved increment settles, offer verified adjacent findings as today. Implement only
the findings the user explicitly selects, keep their verification and fresh scoped code-review
history separate from the increment contract, and then perform the mandatory stop. A selected
finding that changes the technical design still uses the amendment path.

### Ledger, status, and design amendments

One Phase 2 ledger keyed explicitly by the design slug is authoritative for design approval,
increment start, completion, reopening, blocking, invalidation, adjacent-fix cycles, and
integration completion. Every phased `run-start` additionally records the design path and approved
revision, action type (`design`, `increment`, or `integration`), immutable baseline commit/fingerprint, and,
for increment actions, increment ID, explicit plan/walkthrough paths, and settled plan hash. Every
invocation, including a clean increment stop, ends its segment with `run-complete`; that
terminates the invocation segment only, while the design stays active across segments.

Reconstruct phased progress by folding every valid completed and unterminated segment for the
matching design identity across all approved revisions; do not discard completed increment state
merely because its invocation segment ended or a later amendment activated. `amendment` and
`increment-state` events decide which completed increments the active revision invalidates or
reopens. Resume interrupted work only from the latest matching
unterminated action. If the OS purges the ledger, reconstruct conservatively from the approved
design, every retained increment plan/walkthrough checkpoint, and Git evidence; incomplete proof
enters reconciliation rather than inferring success.

The technical design's `Execution Status` section is a human-readable mirror, not a second source
of truth. Status-only updates do not invalidate design review or approval. Resume validates the
mirror against the ledger and Git evidence before trusting it.

A design-changing discovery pauses before additional writes. Amendments are transactional: retain
the last approved governed design as the only executable revision while an OS-temp candidate
records the proposed changes and affected increment IDs. Review the candidate's changed sections
and impacted contracts under the design rubric. Record `proposed`, `reviewed`, `prepared` (user approval), `activated`,
`rejected`, and `aborted` amendment states in the ledger; append the sanitized review/ruling history to the canonical design's
non-governing review section.

The amendment proposal event fingerprints and attributes every live path changed since the active
increment's pre-state. No further implementation writes occur until the amendment settles. Explicit user approval first
appends and fsyncs an `amendment` event with state `prepared`, the prior approved revision, candidate
hash, canonical target path, and temporary replacement path. Preserve a byte-for-byte backup of the
prior approved design beside the canonical file (`.<design-file>.bak`) until activation commits.
Then copy the complete candidate to `.<design-file>.tmp` beside the canonical design, fsync the
file and, where supported, the parent directory (best-effort on Windows, where the write-ahead
`prepared` event plus atomic rename is the guarantee),
compare the canonical governed hash to the prepared event's prior revision, and atomically rename
the replacement over the canonical design. Finally append and fsync the `activated` event and
remove the prior-revision backup.

Startup recovery treats `prepared` without `activated` as follows: before rename, verify the
canonical prior revision and discard or resume the prepared replacement by user ruling; after
rename, verify the canonical candidate hash and append the missing `activated` event; when neither
hash matches, restore neither automatically and enter reconciliation with both preserved copies.
An `activated` event with a canonical hash mismatch also enters reconciliation. Until activation
is durably committed, the prior ledger approval remains authoritative and no implementation
dispatch may proceed.

Rejection, interruption, or abort leaves the proposed revision non-authoritative. The prior design
becomes executable again only when the live diff matches its recorded active-increment state.
Otherwise the ledger remains `needs-reconciliation` and the user must classify the attributed
changes as retained local work, input to another amendment, or work they will remove outside the
workflow. The workflow never removes caller-owned changes automatically. Mark affected pending or
active increments and their downstream dependents invalid only when the replacement revision
activates.

Preserve completed increments only when fresh evidence shows their contracts and shared invariants
remain compatible with the amendment; otherwise reopen them for remediation. Independent completed
increments remain valid.

### Final integration and artifact lifecycle

After the last increment settles, stop as usual. The next
`/implement-dispatch <design-path>` invocation runs the final integration gate only. Freshly verify
cross-increment behavior and, when code review is enabled and available, run the configured final
code-review scope; the sum of individual increment checks cannot replace this gate. When code
review is disabled or its optional companion is unavailable, disclose the skipped review and still
require fresh integration verification.

The final code-review scope is the union of ledger-owned paths from every completed increment,
accepted adjacent-fix cluster, reopened increment, and active integration fix. Review the
design-run baseline commit through current `HEAD` plus working-tree state for that path set, so
committed increments remain visible. Pre-existing or unrelated changes on different paths are
excluded; pre-existing changes and user-retained changes from a rejected or aborted amendment on
an owned path are included conservatively and disclosed. If the
baseline is no longer an ancestor after a rebase or history rewrite, or ownership cannot be
reconstructed, enter reconciliation and require an explicit replacement baseline before review.
The selected scope and baseline identity are immutable for all waves of that final review.

Record final-integration evidence and any enabled review under:

```text
.scratch/plan/<yyyy-mm-dd>-<design-slug>-integration-walkthrough.md
```

Resolve it through the scratch tier with an explicit path and the design slug.

If integration exposes an implementation defect inside an approved increment contract, reopen
that increment and its implementation-plan/review state. If it exposes missing scope, a changed
architecture or shared contract, or a genuinely new increment, use the design-amendment path.
Final completion requires all reopened or amended work to settle and the integration gate to pass
on a later invocation.

Keep the technical design and every increment plan and walkthrough under `.scratch/` through final
integration. Increment stops report but do not relocate them. After final integration settles,
pass every design-run artifact to the existing relocation utility and report every destination.
The ledger is never relocated.

   delivery-phase labels (case-insensitive `\bphases?\s+[0-5][AB]?\b`), per §9's terminology
   rule. Express this spec's cross-phase conditions ("once Phase 1 ships") in shipped prose as
   capability wording (for example "when typed terminal statuses are available") or omit them
   when the capability ships in the same change.
8. Pressure-test new behavioral rules optionally using RED → GREEN → REFACTOR; retain the transcript
   only when it reveals a material failure mode or closes a loophole.

Roll out one phase at a time. A phase is complete only when its completion gate is met and its
documentation matches executable behavior. Treat Phase 5A and Phase 5B as separate gates; do not
start 5B until 5A is green, and do not land either as prose-only behavior.

After Phase 5B passes, perform the v0.4 release packaging as a distinct final step: bump
`package.json` and any lockfile/package metadata to `0.4.0`, update the root `README.md` catalog and
installation/discovery text, regenerate every shipped-skill manifest with `npm run hashes`, run
`npm run validate:configs`, and run `npm test`. The version bump does not land in an earlier phase,
so a partial rollout cannot advertise the complete v0.4 contract. Until then, phases land on `main` but are not released or published; `main` is unsupported for installation, so breaking Phase 1/3 changes never ship under a v0.3 label.
